문장 검토

문장 검토란

에이전트가 작성한 PR 본문, Jira 티켓, Slack 글, 설계 문서는 사용자 이름으로 팀에 게시된다. 그런데 에이전트의 초안에는 출처 없이 채운 세부, 항목을 나열하기만 한 구조, 입말 동사와 비유가 섞이고, 사용자는 같은 지적을 글마다 반복해야 했다.

문장 검토 스킬(polish)은 게시하기 직전의 한국어 글을 사실, 구조, 표현의 세 층 순서로 검토해 수정하는 스킬이다.

  • 사실 층에서는 문장마다 원본 근거가 있는지 확인한다.
  • 구조 층에서는 맥락을 모르는 독자가 항목마다 무엇을 왜 해야 하는지 알 수 있는지 확인한다.
  • 표현 층에서는 문장이 매체에 맞는 문어인지 확인한다.

사용자가 표현을 지적하면 에이전트는 그 지적을 예시 파일로 저장하고, 문장 검토 스킬은 실행할 때마다 예시 파일을 다시 읽는다. 그래서 한 번 받은 지적은 다음 글의 검토 기준이 된다.

구성

polish는 게시할 글의 매체에 맞는 하위 스킬을 선택하고, 신호 체계와 예시 파일을 기준으로 세 층을 검토한다. 게시한 글에 사용자가 표현을 지적하면 polish:capture가 지적을 예시 파일로 저장한다.

응답 문체 규칙은 에이전트가 사용자에게 응답할 때 따르는 문장 규칙이고, 문장 검토 스킬은 같은 규칙을 팀에 게시하는 글에도 적용한다.

세 층 검토

내용이 틀린 문장의 표현만 다듬으면 틀린 내용이 더 그럴듯하게 읽힌다. 그래서 스킬은 사실 층을 먼저 통과한 문장만 구조 층과 표현 층으로 넘긴다.

층판단 기준잡아내는 문제
사실문장마다 원본 근거를 제시할 수 있는가
  • 출처 없이 채운 수치와 원인
  • 확인하지 않은 검증 서술
  • 기억으로 작성한 개수와 상태
구조맥락을 모르는 독자가 항목마다 무엇을 왜 해야 하는지 아는가
  • 한 문장에 세 개 이상 나열한 항목
  • 원인과 결과를 같은 수준에 둔 목록
  • 표의 내용을 다시 서술한 문장
표현매체에 맞는 문어로 정확한 용어를 사용하는가
  • 입말 동사와 비유
  • 번역투와 판에 박힌 문형
  • 화살표, 굵은 글씨, 이모지

사실 층에서 원본으로 판단할 수 없는 문장은 표현을 다듬지 않고, 유지할지 삭제할지 사용자에게 한 문장씩 묻는다.

신호 목록

스킬은 검토에서 찾는 문제를 신호라고 부르고, 지적마다 신호 ID를 기록한다.

신호는 사실 층 8개와 구조 층 12개와 표현 층 9개로 모두 29개다. A-주석필요성은 소스 코드 주석을 검토하는 하위 스킬에서 사용한다.

검토 절차

검토자 한 명이 세 층을 모두 보면 자신이 수정한 문장을 다시 통과시키기 쉽다. 그래서 층마다 별도의 검토 서브에이전트가 같은 글을 검토하고, 앞 층을 통과해야 다음 층으로 넘어간다.

  • 사실 층은 원본으로 판단할 수 없는 문장을 사용자에게 한 문장씩 묻는다.
  • 구조 층은 구조 검사표를 통과할 때까지 재작성과 재검사를 반복한다.
  • 사용자가 구간을 확인하며 지적하면, 수정한 뒤 구조 검사표부터 글 전체를 다시 검사한다.
  • 확정한 문장은 잠그고, 기존 예시에 없는 지적은 polish:capture가 예시 파일로 저장한다.

자율 구현 스킬처럼 사람에게 묻지 않는 실행에서는 사용자 구간 확인만 생략하고 나머지 단계는 그대로 실행한다.

구조 검사표

구조 검사표는 PR 본문과 설계 근거와 상태 서술처럼 목록이나 빈 줄로 구조를 나타낸 글에 적용한다. 항목 하나라도 불합격이면 표현 층의 수정과 검토 완료 판정을 모두 막는다.

ID검사불합격 조건
G1항목 하나에 사실 하나목록 항목 하나에 클래스와 경로와 호출 위치를 쉼표로 나열했다
G2대등한 항목만 같은 수준원인과 결과나 규칙과 예외를 같은 수준의 목록 항목으로 두었다
G3빈 줄만으로 만든 계층 금지제목이나 표나 대등한 목록 없이 빈 줄로만 절을 구분했다
G4같은 내용의 중복 금지같은 목록을 산문과 표로 두 번 작성하면서 판단을 추가하지 않았다
G5변경 이유는 파일 목록이 아님변경 이유의 대부분이 고장 난 동작 대신 파일과 클래스 목록이다
G6맥락 없는 독자의 이해독자가 10초 안에 무엇이 고장 났고 왜 변경이 필요한지 말할 수 없다
G7구체성은 식별자 나열이 아님구체적으로 수정했다면서 동작과 결과 없이 식별자만 추가했다
G8서술 허용훑어볼 같은 형태의 항목이 없는데도 서술을 가짜 목록으로 해체했다

불합격한 글을 재작성할 때는 글의 내용에 따라 형식을 선택한다.

글의 내용선택하는 형식예
대등한 문제가 두세 개같은 수준의 목록 항목PR 변경 이유에 원인이 두 개 있으면 항목 두 개로 작성
동작 하나와 그 결과짧은 서술 한 단락억지로 목록 항목 네 개로 나누지 않음
같은 형태의 데이터 여러 개표나 트리코드 값이나 ID 목록
근거로 제시할 파일과 클래스 위치본문 밖의 표나 부록변경 이유 문장에는 위치 목록을 작성하지 않음
검사표를 이미 통과한 글최소한의 수정취향에 따른 재배치를 하지 않음

서술어 판정표

기계적 표식 검색은 화살표와 굵은 글씨 같은 표식만 찾는다. 그래서 검토자가 수정 대상으로 지목하지 않은 문장의 입말 동사는 예시 파일이 있는데도 반복해서 게시되었다.

서술어 판정표는 문장 끝 서술어와 목록 항목과 표 칸과 제목의 서술어를 빠짐없이 나열하고 하나씩 표시한다.

표시뜻처리
문어매체의 목표 문체에 맞음유지
입말입말 동사나 입말 관용구 또는 문어 대응어가 있는 짧은 동사문어 서술어로 교체하고 문장을 다시 읽음
보존사용자 문장이나 인용이나 보존 대상유지하고 셋 중 무엇인지 밝힘

표시가 없는 서술어나 입말로 남은 서술어가 하나라도 있으면 불합격이다. 글마다 작성한 금지어 목록은 판정표를 대신하지 않는다. 목록은 검토자가 이미 의심한 단어만 포함하기 때문이다.

수정하지 않는 경우

검토는 문제를 빠짐없이 찾되, 아래 경우는 신호로 기록만 하고 수정하지 않는다. 잘못 수정하면 원문이 손상되기 때문이다.

경우처리
보존 대상코드와 수치와 날짜와 고유명사와 식별자와 인용은 수정하지 않는다.
사용자가 선택한 문체매체의 목표 문체와 충돌할 때만 지적하고 결정은 사용자에게 맡긴다. 에이전트가 직접 작성한 초안은 보호 대상이 아니다.
원본 없는 추측 수정사실이 불확실한 문장은 다듬지 않고 사실 층의 판단 불가 항목으로 올린다.
이미 읽히는 서술맥락을 모르는 독자가 목적과 문제와 다음 단계를 이해하면 밀도만을 이유로 문장을 목록으로 해체하지 않는다.

지적의 기록과 등급

검토자는 지적마다 원문과 신호와 등급과 수정안과 이유를 기록한다. 사소한 지적도 삭제하지 않고 등급만 낮춘다.

등급대상
must사실 오류와 독자의 오해와 기계적 표식 위반과 구조 검사표 불합격
minor문체와 남은 구조의 어색함
nit공백과 사소한 군더더기

한 문장에 여러 층의 신호가 함께 있으면 하나로 합치지 않고 층마다 따로 기록한다.

매체별 하위 스킬

매체마다 독자가 기대하는 형식이 달라, 하위 스킬은 공통 신호 체계 위에 매체별 규칙과 예시를 추가한다.

하위 스킬대상추가 규칙
polish:share진행 공유와 주간 보고구간별 구조 규칙
polish:slackSlack 게시 글결론을 첫 줄에 두고 모바일에서 읽히는 배치
polish:ticketJira 티켓 제목과 본문결과만 남기고 선후 관계는 티켓 번호로 연결
polish:comment소스 코드 주석정해진 네 가지 사유가 있을 때만 주석을 허용
polish:capture사용자 피드백지적이나 칭찬을 예시 파일로 저장

주석 가드 훅이 소스 파일에 주석을 추가하는 편집을 거부하면, 에이전트는 polish:comment로 주석이 필요한지 먼저 판단한다.

예시 파일

규칙 문장만으로는 어떤 표현이 문제인지 사람마다 다르게 판단한다. 그래서 스킬은 사용자가 실제로 지적하거나 칭찬한 문장을 예시 파일로 보관하고, 검토할 때마다 모든 예시 파일을 다시 읽는다.

  • 예시 파일 하나는 지적 하나를 다루고 아래 서식의 항목을 기록한다.
  • 어떤 글에나 적용되는 예시는 공통 예시 폴더에, 특정 매체에서만 성립하는 예시는 해당 하위 스킬의 예시 폴더에 둔다.
  • 입말 동사를 알리는 훅은 예시 파일에 기록된 입말 목록을 기준으로 게시 명령과 응답을 검사한다.
항목기록하는 내용
판정좋음이나 나쁨이나 미해결
신호신호 목록의 ID
구간도입부나 본문 일반처럼 글에서 표현이 놓인 위치
매체문서나 Slack 진행 공유나 보고나 Jira 티켓
맥락표현이 어디서 왜 나왔는지
표현실제 문장의 인용
피드백좋거나 나쁜 이유와 사용자 피드백의 요지
개선수정한 문장이고 좋음이면 유지라고 기록
원칙일반화한 한 줄 규칙

파일 이름은 NN-판정-구간-제목.md 형식이다. 미해결은 사실이 확정되지 않아 개선문을 작성할 수 없는 예시이고, 사실이 확정되면 나쁨으로 갱신한다.

예시는 정답이 아니라 참고 자료이므로 검토자는 문장을 그대로 옮기지 않고 구조와 원칙만 적용한다. 예시 파일은 공통 예시 74개와 하위 스킬 예시 19개다.

검토 방법의 평가 기록

지금의 검토 절차는 2026-07-31에 검토 방법 후보를 1단계부터 3단계까지 비교해 선택했다. 모든 단계는 같은 평가용 글과 같은 채점 기준을 사용했다.

평가용 글은 PR 본문의 변경 이유 절을 결함 유형별로 변형한 여섯 개다.

변형결함
V0추상적인 서술
V1목록 항목 안의 식별자 나열
V2대등하지 않은 항목을 같은 수준에 둔 목록
V3산문과 표의 중복
V4빈 줄만으로 구분한 구조
V5결함 없는 서술

채점은 8개 항목에 40점 만점이다. V1부터 V4까지의 수정본이 32점 이상이면서 V5가 28점 이상을 유지하면 종료하고, 항목 R2와 R4와 R5와 R7은 각각 4점 이상이어야 한다.

1단계는 라운드마다 후보를 비교하고, 1위 후보에 남은 위험을 다음 라운드 후보로 시험했다.

선택한 H2b는 표현 검토 전에 구조 검사표를 적용하고, 국소 피드백 뒤에는 구조 검사표를 글 전체에 다시 적용한다. 이 결정은 스킬 문서의 구조 검토 설명과 수정하지 않는 경우와 검토 절차에 반영되었다.

2단계는 작성 에이전트 10개와 채점 에이전트 20개로 검토 방법 다섯 개를 다시 비교했다. 작성 에이전트는 방법 하나를 두 개씩 맡아 여섯 글을 수정했고, 채점 에이전트는 수정본을 R1~R8 기준으로 채점했다.

두 에이전트는 같은 사실 목록과 구조 검사표 G1~G8과 고정된 출력 형식을 사용했다. V0~V4 점수는 변형별 중앙값의 평균이고, V5 점수는 중앙값이다.

3단계는 규칙으로 수정본을 만드는 작성기와 규칙 기반 채점기로 300라운드를 실행했다. 라운드마다 검토 방법의 설정값을 바꾼 후보를 만들어 채점했다.

마지막 라운드의 1위는 목록 선호와 표 강제 같은 설정을 모두 끈 문단형이었고, 여섯 글 모두 40점이었다. 대등 목록형과 최소 수정형도 최고점에 도달했다.

자동 채점에서는 빈 줄로 나눈 문단형이 높은 점수를 받았지만, 문단형은 사용자가 받아들인 PR 변경 이유 형식과 맞지 않았다. 그래서 스킬은 대등한 축이 두세 개이면 목록을 선택하고, 동작 하나를 설명하면 서술을 선택한다.

V1을 최종 형식으로 수정한 결과는 다음과 같다. 클래스 이름은 일반화했다.

수정 전
- main 기준 프로덕션 곳곳에서 LocalDateTime.now() 와 UUID.randomUUID() 를 직접 호출한다. 예: EntityA 만료 시각 기본값, ForkSupport fork 시각·새 식별자, ServiceA 생성, ServiceB 목록 기준 시각, ClientA 추적 식별자, DisplayerA·CacheA 캐시 시각, ServiceC 추천 키, AuditCallback·DbConfig 감사 시각.
- ServiceD 는 ServiceA 를 @Lazy 로 받아 조립 순환을 숨긴다.
- 위 값들을 코드가 스스로 만들면 단위 테스트에서 시각·식별자를 고정하기 어렵고, 같은 패턴의 신규 코드가 계속 쌓여도 막을 규칙이 없다.
수정 후 (최종 형식)
- 세션·캐시·외부 연동마다 시각과 식별자 원천이 흩어져 있다. 테스트에서 값을 고정하기 어렵고, 같은 직접 호출을 막는 빌드 규칙도 없다.
- 한 서비스가 다른 서비스를 @Lazy 로 받아 조립 순환을 감춘다.
- 이 PR은 원천을 configuration 주입으로 모으고, 순환을 구조로 끊은 뒤, 재발을 규칙으로 막는다.
