설계와 검증

설계와 검증이란

에이전트가 구현을 마쳤다고 보고해도, 무엇을 만들기로 했는지와 그것을 실제로 확인했는지가 기록으로 남지 않으면 결과를 믿기 어렵다. 그래서 이 환경은 구현 전에 동작을 정하는 설계 문서와, 구현 뒤에 실제 요청으로 동작을 확인하는 검증 케이스를 토픽 안에 남긴다.

설계 문서는 설계 작성 스킬(topic:design)이, 검증 케이스는 케이스 작성 스킬(topic:cases)이 작성하고, 설계 문장 대조표가 두 산출물을 잇는다. 세 산출물은 토픽 스킬의 하위 기능이라 따로 사용할 수 있고, 자율 구현 스킬은 설계 단계와 검증 케이스 단계에서 이 기능을 호출한다.

구성

설계 문서는 구현 전에, 검증 케이스와 대조표는 구현 뒤에 작성하고, 산출물마다 형식을 확인하는 검사 스크립트가 있다. 아래 도해는 어느 시점에 어떤 검사가 무엇을 검출하는지 보인다.

갱신 알림 훅은 토픽 파일을 작성할 때마다 토픽 검사기(topic-lint.py)를 실행하고, 토픽 검사기가 설계 문서 검사기와 케이스 검사기를 함께 실행해 위반을 알린다. 훅이 위반을 알려도 작업은 계속 진행되며, 훅의 동작은 토픽 탭의 갱신 훅 절에서 설명한다.

설계 문서

설계 단계에서 에이전트는 구현 전에 동작을 문장 단위로 정한 설계 문서를 토픽의 design 폴더에 작성한다(설계 작성 스킬 topic:design). 구현 단계는 이 문서를 기준으로 코드를 작성하고, 문서가 확정되면 Jira 티켓 본문도 이 문서를 변환한 내용으로 바뀐다.

설계 문서가 토픽마다 다른 모양이면 검사기로 검사할 수도, 티켓 본문으로 옮길 수도 없다. 그래서 모든 설계 문서는 같은 양식을 따르고, 설계 문서 검사기(design-doc-lint.py)가 양식을 검사한다.

상태

설계 문서의 머리 정보에는 상태가 있고, 자율 구현 스킬은 상태를 보고 구현 기준이 되는 문서 하나를 고른다.

상태뜻
초안작성 중이다.
확정구현 기준이다. 확정 전에 검토를 거친다.
완료구현이 끝났다.
폐기쓰지 않는다.
대체다른 설계 문서로 대체되었다.

자율 구현 스킬은 확정이나 초안 문서 가운데 하나를 구현 기준으로 고르고, 없으면 새 문서를 작성한다.

구성

설계 문서는 이름과 순서가 정해진 절 17개로 나뉜다.

절기록하는 것
Summary무엇을 하는 설계인지와 왜 필요한지 두 줄
Context설계가 필요해진 배경
Goals이 설계가 달성할 것
Non-Goals이 설계가 다루지 않는 것
Design영역별 동작과 흐름 도해
InterfaceAPI, 메서드 시그니처, 의사 코드, 바꿀 파일 목록
Evidence설계 판단의 근거가 된 측정 결과
Alternatives검토한 대안과 판정
Consequences설계를 적용한 뒤 달라지는 것
Milestones마일스톤과 완료 기준 표
Dependencies다른 작업이나 시스템에 의존하는 것
Risks예상되는 위험
Rollback문제가 생겼을 때 되돌리는 방법
Verification구현을 확인하는 방법
Open Questions아직 답하지 못한 질문
Revision History변경 이력과 검토 기록
Appendix본문에 적지 않은 코드 위치 표

작성 규칙

절의 이름만 정해 두면 문서마다 길이와 밀도가 달라지고, 구현과 검토가 기댈 문장이 흐려진다. 그래서 설계 작성 스킬의 지침은 아래 규칙을 정하고, 설계 문서 검사기는 양식, 항목 수, 코드 이름 수, 표 위치, 측정 번호, 도해 유무를 오류로 검사한다.

대상규칙
양식
  • 머리 정보는 문서 종류, 상태, 수정 시각 세 필드만 둔다.
  • 절 17개를 정해진 이름과 순서로 모두 둔다.
  • 내용이 없는 절에는 '- 없음'을 적는다.
Summary
  • 정확히 두 항목을 둔다.
  • 첫째 항목에 무엇을 하는 설계인지, 둘째 항목에 왜 필요한지 적는다.
Design
  • 첫 영역은 흐름 도해만 둔다.
  • 배치, 입력, 처리, 출력, 오류 처리 다섯 영역은 반드시 채운다.
  • 캐시, 동시성, 호환성, 보안 같은 선택 영역은 해당할 때만 정해진 순서로 둔다.
  • 처리 영역은 항목 8개, 다른 영역은 항목 5개까지 둔다.
서술 절
  • Context, Design, Interface, Consequences, Risks, Rollback, Verification은 문단 없이 항목으로만 작성한다.
  • 항목 하나에는 한 문장, 사실 하나만 적는다.
  • 절마다 항목 수 상한을 지킨다(예: Context 4개, Risks 4개, Rollback 3개).
본문 전체
  • 로컬 파일 경로, 업무 노트 경로, 사람 이름을 적지 않는다.
  • 클래스 이름 같은 코드 이름은 절마다 3개까지만 적고, 나머지는 Interface와 Appendix에 둔다.
  • 외부 근거는 Confluence 주소나 Jira 키로만 가리킨다.
표
  • 연동 지점, 파일 목록, 상태 기록, 측정, 부록 표는 정해진 절에만 둔다.
측정
  • 수치를 말하는 항목에는 측정 번호를 붙인다.
  • 측정 표에는 날짜, 표본과 크기, 호출 조건, 정답 기준, 결과 건수를 적는다.
  • 비교하는 측정은 같은 입력으로 같은 시점에 다시 실행한다.
파일 목록
  • 구현이 만들거나 바꿀 파일마다 책임과 따로 둔 이유를 한 문장씩 적는다.
  • 구현 단계는 이 표를 파일 구조의 기준으로 삼고, 표에 없는 파일이 필요하면 설계를 먼저 수정한다.
흐름 도해
  • 기존 경로를 바꾸면 변경 전과 변경 후 도해를 둘 다 둔다.
  • 도해는 상자와 화살표를 적은 원본 파일에서 스크립트로 생성하고, 손으로 그리지 않는다.
  • 판단 상자는 처리와 오류 처리 영역의 항목에서만 나온다.
  • 도해 아래에 도해가 답하는 질문과 보여 주지 않는 범위를 한 줄씩 적는다.
Alternatives
  • 대안마다 판정을 적고, 기각했으면 기각 사유를 적는다.

확정 전 검토

설계를 쓴 에이전트가 스스로 확정하면 자기 판단의 빈틈을 보지 못한다. 그래서 확정 전에 설계를 쓰지 않은 서브에이전트가 코드를 함께 보며 아래 질문으로 검토하고, 지적은 Alternatives나 Open Questions에 남긴다.

  • 값이 처음 잘못 만들어지는 지점에서 고치는가, 나중에 덮어쓰는가.
  • 같은 종류의 결함이 설계가 건드리는 다른 함수와 파일에도 있는가.
  • 다른 파일이 정한 값 규칙에 기대는 조건이 있는가.
  • 오류 처리 항목과 도해의 판단 상자가 하나씩 대응하는가.

함께 실행하는 다른 서브에이전트는 변경 후 도해만 보고 도해가 내리는 결정을 한 문장으로 작성한다. 에이전트는 그 문장을 Design 항목과 대조한다.

검토 결과는 Revision History에 기록한다.

확정한 문서의 Design, Interface, Milestones를 수정하면 도해를 다시 생성하고 다시 검토한 뒤 Jira 본문도 수정한다.

검증 케이스

검증 케이스는 구현한 기능에 실제 요청을 보내고 받은 응답 원문으로 동작을 판정한 기록이고, 케이스 작성 스킬(topic:cases)이 작성한다. 실행 전에 예상한 기대 결과로는 실제 동작을 확인할 수 없으므로, 요청을 먼저 실행하고 응답을 확인한 뒤에 기대 결과를 확정한다.

케이스마다 파일 하나를 두고, 케이스 목록 파일에 케이스별 결과와 결과별 건수를 기록한다.

항목기록하는 것
Spec Intent케이스로 확인하려는 의도
Spec Action보낼 요청
Spec Expect번호를 매긴 기대 결과
Outcome Observation로컬과 개발 환경에서 실제로 받은 응답과 로그
Outcome Checks기대 결과 번호마다 판정과 근거

필수 케이스는 머리 정보에 required: Y로 표시한 케이스이고, 설계 문서의 필드 계약과 오류 처리 문장에서 도출한다. 자율 구현 스킬은 필수 케이스가 실패하면 구현 단계를 다시 실행해 코드를 수정한 뒤 다시 확인한다.

설계 문장 대조표

케이스만 보고는 설계 문서의 동작을 모두 확인했는지 알 수 없다. 그래서 검증 케이스를 작성할 때 설계 문서의 동작 항목마다 어떤 방법으로 확인했는지 적은 대조표를 작성한다. 예를 들어 "숙소 조회가 실패하면 만료로 응답한다"는 항목에는 이를 확인한 케이스 번호를 적는다.

대조표 검사기는 아래 두 가지를 수행한다.

  • 설계 문서의 동작 항목을 읽어 빈 대조표를 만든다.
  • 검사할 때는 동작 항목마다 같은 문장이 적힌 행을 찾아 아래 규칙을 확인한다.

행이 없는 문장도 위반이므로, 설계 문장을 수정하면 대조표 행도 함께 수정한다.

검증 칸근거 칸위반
케이스실행한 케이스 번호번호가 없거나 실행 전 케이스다.
단위테스트 이름과 사유:사유가 없다.
해당없음사유:사유가 없다.

배치, 출력, 오류 처리, 호환성 영역에서 단위 테스트나 해당없음으로 적은 행에는 실제 요청으로 재현해 보려 한 내용도 적는다. 시도하지 않았다면 그 사실을 적어도 통과한다.
