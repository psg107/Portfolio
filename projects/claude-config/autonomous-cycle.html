자율 구현

자율 구현 스킬이란

자율 구현 스킬은 에이전트가 다이나믹 패키지 백엔드 티켓 하나를 조사부터 개발 환경 검증까지 진행할 수 있게 하는 체계다. 입력은 요청 문장 하나이고, 산출물은 아래 네 가지다.

  • 설계 문서
  • 커밋
  • PR
  • 개발 환경 검증 결과

앞서 설명한 기능의 호출

자율 구현은 앞서 설명한 토픽, 설계와 검증, 코드 리뷰, 문장 검토 기능을 단계마다 호출해 조합한다. 진행 상태는 토픽의 상태 문서에 기록하고, 설계와 검증은 설계와 검증의 설계 문서와 검증 케이스로, 리뷰는 코드 리뷰의 두 스킬로 수행하고, 커밋 메시지와 PR 본문과 결과 보고는 문장 검토를 거쳐 게시한다.

아래 절은 자율 구현이 네 기능을 어떤 순서로 호출하는지와 자율 구현에만 적용되는 규칙을 설명한다.

사람의 판단이 필요한 경우

목표는 사용자가 다음에 세션을 열었을 때 개발 환경 검증까지 완료된 상태다. 사람의 판단이 필요한 경우는 아래 두 가지다.

  • 세션 연결, 티켓 키, 현재 폴더 어디에서도 작업할 토픽을 정할 수 없고 새 토픽을 만들라는 요청도 없는 경우. 이때 스킬은 최근 토픽 목록을 한 번 제시한다.
  • CI 실패, 필수 검증 케이스 실패, 로컬 서버 기동 실패가 자동 재시도로 해결되지 않는 경우.

구성

자율 구현 스킬은 아래 네 구간의 단계를 차례로 실행하고, 단계마다 코드 리뷰 스킬(pr:nitpick)이나 PR 생성 스킬(pr:create) 같은 전용 스킬을 호출한다.

스킬은 시작할 때 요청 문장을 읽어 아래 네 가지를 정한다.

  • 종료점: 개발 환경 검증까지 진행할지, PR까지만 진행할지
  • 실행 위치: 현재 세션에서 진행할지, 새 터미널 탭의 세션에서 진행할지
  • 토픽: 진행 상태를 기록할 토픽
  • 기준 브랜치: 작업 브랜치를 만들고 PR을 올릴 대상 브랜치

요청에 'draft만'이나 '배포 없이' 같은 표현이 있으면 종료점은 PR이 된다. 이때는 개발 환경 구간(15~17단계)을 생략하고, 로컬 검증 결과만 PR 댓글로 남긴다.

단계 흐름

준비와 설계

요구 수집은 요청 문장과 토픽과 Jira에서 값을 정하고, 정하지 못한 값은 추정하거나 다음 단계에서 생성한다. 조사는 여러 출처를 함께 확인하도록 출처마다 서브에이전트를 병렬로 실행하고, 설계는 설계와 검증 탭의 설계 문서 양식으로 작성한다.

구현과 로컬 검증

PR을 열기 전에 로컬에서 리뷰와 실제 요청 검증을 마쳐, 실제 요청으로 확인한 변경만 푸시한다. 로컬 리뷰는 코드 리뷰 탭의 관점별 리뷰를 PR 없이 실행하고, 검증은 설계와 검증 탭의 검증 케이스와 대조표를 작성한다.

필수 케이스가 실패하면 코드를 수정하고 검사와 케이스를 다시 통과한 뒤에 푸시한다.

PR

PR은 draft로 열고, CI 통과와 셀프 리뷰를 마친 뒤에 리뷰 준비 완료로 변경한다. 다른 개발자에게 리뷰를 요청하기 전과 개발 환경에 배포하기 전에 셀프 리뷰 지적을 처리하기 위해서다.

셀프 리뷰는 코드 리뷰 탭의 두 스킬을 한 라운드로 반복한다.

개발 환경

개발 브랜치에 커밋이 있어도 CI가 취소되면 배포가 실행되지 않으므로, CI 성공과 배포 완료를 확인한 뒤에 검증한다. 검증은 로컬에서 실행한 케이스를 호스트만 변경해 다시 실행하고, 케이스 문서를 그대로 PR 댓글로 남긴다.

리뷰 규칙

자율 구현은 리뷰를 두 번 한다. PR을 만들기 전에 로컬 변경을 리뷰하고, PR을 연 뒤 같은 PR을 다시 리뷰한다.

두 리뷰에는 아래 규칙이 적용된다. 리뷰는 코드 리뷰 스킬(pr:nitpick)이, 지적 처리는 지적 처리 스킬(pr:resolve)이 수행하며, 두 스킬의 동작은 코드 리뷰 탭에서 설명한다.

대상규칙
로컬 리뷰 기록
  • 리뷰 기록 검사기가 통과해야 로컬 리뷰 단계가 완료된다.
  • 기록된 서브에이전트 수가 2 미만이면 검사가 실패해 한 번 읽고 종료한 리뷰를 차단한다.
  • 기각한 지적에 같은 번호의 반박 줄이 없으면 검사가 실패한다.
PR 셀프 리뷰
  • CI 통과 뒤 열린 PR의 diff를 같은 리뷰 스킬로 다시 검토한다.
  • 리뷰 한 번과 지적 처리 한 번을 한 라운드로 최대 3라운드 반복한다.
  • 지적이 남지 않은 라운드에서 종료한다.
3라운드 뒤 남은 지적
  • PR을 draft로 유지하고 남은 항목을 사용자에게 보고한다.

스스로 판정하는 기준

에이전트에게 티켓 구현을 요청하면, 에이전트가 남은 단계를 나열한 보고로 응답을 종료하거나 진행해도 되는지 다시 묻는 일이 발생한다. 자료를 찾지 못하면 임시 값을 사용하고 다음 단계로 진행하기도 한다.

사람이 중간에 확인하지 않아도 티켓이 완료되려면, 에이전트가 단계의 완료 여부와 진행할 수 없는 지점의 처리 방법을 스스로 판정할 기준이 필요하다. 그래서 스킬은 아래 장치를 둔다.

  • 단계마다 다시 확인할 수 있는 통과 증거를 요구하고, 증거가 남은 단계만 완료로 표시한다.
  • 자료를 찾지 못하거나 설계와 코드가 일치하지 않는 지점에서는 정해진 절차로 근거를 다시 조사해 판정한다.
  • 진행 상태를 토픽의 상태 문서에 기록하고, 턴을 종료하기 전에 현재 단계를 읽어 다음 단계를 이어 실행한다.
  • 티켓이 없으면 Jira 티켓을, 세션에 연결된 토픽이 없으면 새 토픽을 생성하고 진행한다.

통과 증거

사람이 단계마다 결과를 확인하지 않으므로, 스킬은 단계마다 남겨야 할 증거를 정해 두고 증거가 있는 단계만 완료로 표시하도록 지시한다. 증거는 검사기 실행 결과, PR 주소처럼 나중에 다시 확인할 수 있는 것이다.

에이전트는 턴을 끝내기 전에 상태 문서에서 현재 단계를 읽고, 종료점에 도달하지 않았으면 다음 단계를 같은 턴에서 실행한다. 단계를 건너뛰거나 남은 단계만 보고하고 멈추는 일을 막기 위해서다.

단계통과 증거
4 설계
  • 설계 문서 검사기(design-doc-lint.py) 통과
  • 설계 문서의 도해가 도해 원본 파일에서 다시 생성한 결과와 같음(diagram-gen.py check)
  • 설계 문서를 변환한 결과와 같은 Jira 티켓 본문
5 구현
  • 설계 문서가 바꾸겠다고 적은 파일마다 대응하는 커밋
6 로컬 리뷰
  • 리뷰 기록
  • 지적별 수정이나 반박 기록
  • 리뷰 기록 검사기(nitpick-lint.py) 통과
7 단위와 정적 검사
  • 이 세션에서 실행한 테스트와 커버리지 통과
8 검증 케이스
  • 케이스의 로컬 관측 기록
  • 대조표 검사기(case-coverage-lint.py) 통과
9 HTTP 요청
  • 케이스 문서에 적은, 그대로 실행할 수 있는 HTTP 요청
10 커밋과 푸시
  • 브랜치 커밋과 푸시 성공
11 draft PR
  • PR 주소
12 CI 확인
  • PR CI 통과
13 PR 셀프 리뷰
  • 라운드별 리뷰 기록 또는 지적 없는 라운드의 조기 종료 기록
14 리뷰 준비 완료
  • draft가 아닌 PR
15 개발 환경 반영
  • 개발 브랜치 커밋과 CI 성공
16 배포 대기
  • 배포 성공
17 개발 환경 검증
  • 케이스의 개발 환경 관측 기록
  • PR 댓글 주소
18 마무리
  • 종료 단계까지의 증거

모든 단계는 상태 문서 갱신을 증거로 요구하고, 단계 1부터 3은 상태 문서 갱신만 요구한다. 통과 기록은 이 세션에서 실행한 것만 인정한다.

막힐 때의 절차

에이전트가 혼자 진행하다 막히면 작업을 보류하는 문장을 작성하거나, 빌드만 통과하도록 임시 값을 넣기 쉽다. 그래서 스킬 문서는 보류 문장과 임시 값 수정의 예를 표로 적어 두고, 작성하려는 문장이나 수정이 표의 예에 해당하면 아래 절차를 먼저 따르라고 지시한다. 해당하는지는 에이전트가 지침을 읽고 스스로 판단한다.

절차가 끝나면 같은 턴에서 작업을 이어 간다.

보류 전 재조사

스킬 문서는 "출처 없음", "나중에 처리", "확인 필요", "담당자 확인 후" 같은 보류 문장을 예로 들고, 에이전트에게 이런 문장을 작성하기 전에 이 절차를 따르라고 지시한다. "찾아봤는데 없다"는 판단은 검색어를 정한 에이전트 자신이 내리므로 신뢰할 수 없기 때문이다.

  1. 조사 출처(실제 API 호출, API 명세, Confluence, 코드, Jira, Slack)마다 서브에이전트를 실행하고, 서브에이전트 전체가 서로 다른 검색어를 20개 이상 사용한다.
  2. 1차 조사에서 새로 나온 식별자, 테이블 이름, 문서 제목으로 다시 조사한다. 출처를 찾으면 찾은 값으로 작업을 계속한다.
  3. 그래도 찾지 못하면 관점이 다른 검토 서브에이전트 세 개가 출처가 정말 없는지 반박을 시도하고, 세 개 모두 통과시켜야 보류 문장을 작성한다.
  4. 조사에 사용한 에이전트 수, 검색어 수, 검토 판정을 토픽에 기록한다.

설계 불일치 정지

스킬 문서는 설계 문서와 코드나 실제 데이터가 서로 다른 값을 말하는 경우와, 값을 모르는 채 0이나 빈 값이나 임의의 기본값을 넣는 수정과 코드가 반환하는 값으로 테스트 기대값을 변경하는 수정을 예로 들고, 에이전트에게 이런 경우에는 코드를 편집하기 전에 이 절차를 따르라고 지시한다. 이런 수정은 빌드를 통과하지만 틀린 금액 같은 결과를 그대로 배포하기 때문이다.

  1. 코드 편집을 멈추고, 무엇이 맞지 않는지 양쪽 값을 넣어 한 문장으로 작성한다. 예를 들면 "금액 계산에 사용하는 값을 0으로 두면 금액이 변경되지 않는데, 정책 문서는 그 값을 0이 아닌 계산 결과로 정의한다."이다. 이 문장을 작성하지 못하면 실제로 맞지 않는 것이 아니므로 편집을 계속한다.
  2. 설계 문서, 토픽 용어 문서, 티켓 본문, 실제 시스템 응답 순서로 어느 쪽이 맞는지 근거를 찾는다. 어디에서도 찾지 못하면 보류 전 재조사를 실행한다.
  3. 판정에 따라 코드, 설계 문서, 용어 문서 가운데 하나만 수정한다. 두 해석을 설정값으로 함께 남겨 두는 수정은 해결로 인정하지 않는다.
  4. 1단계에서 작성한 문장, 확인한 출처, 판정 근거, 수정한 문서를 기록하고, 이 기록이 있어야 해당 단계가 완료된다.
