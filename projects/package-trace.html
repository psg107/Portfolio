사내 문의 자동응답 에이전트란

여행 패키지 사업부는 상품이 판매되지 않거나 예약이 취소된 이유를 Slack으로 개발팀에 문의한다. 답을 확인하려면 개발자가 데이터와 코드를 직접 조회해야 하므로 건당 30분에서 2시간이 소요된다.

판매 날짜가 화면에 표시되지 않는다는 문의를 개발자 여러 명이 주말에 조사한 결과, 재고가 0이어서 판매가 중단된 정상 동작이었던 경우도 있었다. 이런 문의의 답은 문의한 상품의 현재 값과 그 값을 판단하는 코드의 조건을 대조해야 확인된다.

이 에이전트는 문의를 읽고 사내 서비스의 실제 데이터와 소스 코드를 조회한 뒤, 근거가 갖춰진 내용과 추정을 구분한 답변을 Slack에 게시하는 서버다. 현재 로컬 환경에서 동작을 확인한 단계이고, 서버 배포와 문의 채널 답변 게시와 실제 문의 기준의 품질 검증은 진행되지 않았다.

구성

호출 순서를 지시하는 에이전트(Orchestrator)는 데이터 수집(Collector)과 소스 탐색(Tracer)과 판정(Concluder)을 맡은 에이전트를 도구처럼 호출한다. LLM 호출은 사내 LLM 게이트웨이를 거쳐 Claude로 전달된다.

Collector는 상품 서비스와 예약 서비스와 공급사 연동 서비스의 API에서 현재 값을 조회하고, Tracer는 소스 색인을 조회한다. 소스 색인은 클래스와 함수 이름(심볼)의 위치와 호출처를 파일 원문과 함께 저장한 MongoDB 데이터다.

문서 검색에서 실행 시점 조회로

첫 시도인 AI 챗봇 문서 학습 서비스는 Jira와 Confluence와 PDF 문서를 벡터로 저장하고 질문과 유사한 문서를 LLM에 전달하는 RAG 챗봇이었다. 답변 품질이 기대에 미치지 못해 실제 문의 응답에 투입되지 않았고, 품질 수치와 질문별 기록이 없어 품질 미달의 원인은 추정 수준이다.

전환의 근거는 적재 대상의 범위다. 이 챗봇에는 문서만 적재되고 소스 코드와 현재 데이터는 포함되지 않으므로, 문의한 상품의 현재 값과 코드의 조건을 대조해야 하는 문의는 검색을 개선해도 답할 수 없다.

재순위화와 하이브리드 검색은 적용되지 않았으므로 문서에 답이 있는 질문에 대한 RAG의 개선 여지는 확인되지 않은 채 남아 있다. 도메인 지식 전체를 시스템 프롬프트에 포함하는 구조는 현재 값을 제공하지 못하고 컨텍스트 한계와 비용과 수동 갱신 부담이 따른다.

이 에이전트는 문의를 처리하는 시점에 도구를 호출해 데이터와 코드를 조회한다. 문의 1건이 에이전트 4개의 반복 호출로 이어지므로 LLM 호출 수가 문서 검색 방식보다 많고, 실제 문의 기준의 비용은 측정되지 않았다.

증거 수집과 판정의 분리

잘못된 정보로 답변하면 답변하지 않는 경우보다 결과가 나쁘므로, 판정은 변형되지 않은 증거를 기준으로 수행되어야 한다. 그래서 수집과 탐색과 판정을 별도 에이전트로 나누고 Orchestrator에는 중간 결과를 원문 그대로 전달하도록 지시한다.

에이전트 1개가 조회와 탐색과 판정을 함께 수행하는 구조와 비교하면, Concluder에는 데이터 조회 도구가 등록되지 않으므로 판정의 입력은 전달받은 증거와 파일 읽기 결과로 한정된다.

에이전트주요 도구반환하도록 지시한 값
Collector사내 서비스 조회 도구 10개해석하지 않은 조회 원본
Tracer심볼과 호출처와 키워드 조회, 파일 읽기파일과 행 번호와 코드 인용
Concluder파일 읽기판정과 근거를 갖춘 결론

분리 규칙은 코드로 강제되는 것과 프롬프트 지침에 의존하는 것으로 나뉜다.

규칙보장 수단내용
도구 범위코드에이전트는 자신에게 등록된 도구만 호출한다.
조회 전용코드사내 서비스 클라이언트에는 조회 요청만 구현되어 있다.
결과 우선코드Concluder를 호출한 경우 그 결과를 Orchestrator의 응답보다 우선해 답변으로 사용한다.
호출 순서지침수집 1회와 탐색 최대 2회와 판정 1회의 순서로 호출한다.
원문 전달지침Orchestrator는 도구 반환값을 수정하지 않고 Concluder에 전달한다.
결론 금지지침Collector와 Tracer는 원인과 결론을 작성하지 않는다.

Concluder의 호출 여부는 지침에 속하므로 코드의 보장은 Concluder를 호출한 문의에만 적용된다. 로컬 테스트에서는 Orchestrator가 Concluder를 호출하지 않고 종료한 사례가 있었고, 이 경우 판정을 거치지 않은 Orchestrator의 응답이 답변이 된다.

이 대체 경로는 잘못된 답변이 무응답보다 나쁘다는 기준과 어긋나고 게시 메시지에도 구분 표시가 없어, 로컬 단계의 미해결 사항으로 남아 있다. 원문 전달도 Orchestrator의 LLM이 도구 인자를 작성하는 경로이고 코드는 동일성을 검사하지 않는다.

이 단방향 흐름은 데이터와 사용법 문의를 대상으로 동작하고, 오류가 로그에만 있는 장애 문의에는 확인됨 판정을 내릴 수 없다. 증거가 부족할 때 로그를 조회하고 코드를 다시 탐색하는 반복 구조는 검토 단계이고, 탐색이 목적에서 벗어나거나 반복 한도를 초과할 때의 종료 조건이 정해지지 않았다.

확인됨과 추정의 판정

Concluder는 주장마다 확인됨 또는 추정으로 판정한다. 확인됨은 코드의 조건문과 실제 데이터 값을 추론 없이 대조할 수 있을 때만 허용한다.

추정만 있는 결론은 사업부 메시지에서 불확실 표현으로 작성한다. 계산으로 얻은 수치도 항상 추정이다.

답변은 메시지 2개로 게시된다. 사업부에는 파일 이름과 필드 이름을 제외한 2~4문장을 게시하고, 개발자에게는 판정과 근거 전체를 그 메시지의 스레드로 게시한다.

이 기준은 정확도를 우선하므로 호출 체인이 복잡한 문의에서 Tracer가 반복 한도 안에 코드를 찾지 못하면 결론 전체가 추정으로 작성된다.

판정 기준은 Concluder 프롬프트에 있고 코드는 인용의 실재를 검사하지 않으므로 판정의 정확도는 LLM이 지침을 따르는 정도로 결정된다. 개발자 스레드에는 파일 위치와 조건문 인용이 포함되므로 판정을 코드와 직접 대조할 수 있다.

소스 색인의 증분 갱신

Tracer가 코드를 탐색하려면 심볼의 위치와 호출처를 즉시 조회해야 한다. 사전 색인 없이 탐색하는 방식에는 각각 제약이 있다.

방식제약
GitHub Code Search API분당 10회 제한이 있어 탐색을 반복하는 에이전트의 병목이 된다.
grep 순차 탐색탐색 자체에 토큰과 시간이 소모된다.
clone과 ctags배포 대상으로 계획한 ECS 컨테이너가 재시작될 때마다 clone이 사라진다.

소스 색인은 GitHub API로 Kotlin 파일을 수신해 정규식 파서로 심볼을 추출하고, 파일 원문과 심볼과 호출처를 MongoDB에 저장한다. 저장소마다 마지막으로 색인한 커밋을 기록하고 최신 커밋과 비교해 변경된 파일만 다시 파싱한다.

심볼 조회와 호출처 조회와 키워드 검색은 MongoDB만 조회하고, 파일 읽기도 저장된 원문을 먼저 사용하므로 탐색 중 GitHub API 호출은 원문이 없는 파일로 한정된다.

정규식 파서는 참조를 이름의 일치로 판단하므로 같은 이름의 다른 심볼도 호출처로 기록된다. Tracer에는 파일 읽기로 실제 코드를 확인한 뒤 인용하도록 지시하므로 이 오차는 호출처 후보가 증가하는 형태로 나타난다.

색인 대상이 Kotlin 파일로 한정되므로 프론트엔드 코드의 제약은 탐색되지 않는다. 갱신은 HTTP 요청으로 실행되므로 요청 전까지 색인은 이전 커밋 기준이다.

탐색 주의 사항 저장

문의마다 처음부터 탐색하면 같은 탐색 오류를 반복하므로 Tracer는 탐색 주의 사항을 저장한다. 탐색 주의 사항은 같은 이름의 클래스가 여러 위치에 있거나 진입점이 예상과 달라 잘못된 코드를 먼저 탐색한 경우의 기록이고, 다음 탐색의 시스템 프롬프트에 포함된다.

코드에서 확인할 수 있는 결론은 저장 대상이 아니다. 저장된 결론이 실제 데이터와 충돌하면 에이전트가 저장된 결론에 치우치므로 코드를 기준 원본으로 둔다.

저장된 항목은 모두 프롬프트에 포함되므로 항목 수가 증가하면 Tracer의 입력도 증가한다.

문의 수신

문의자는 문의를 게시한 뒤 스레드 댓글로 추가 정보를 작성하는 경우가 많으므로, 에이전트는 문의 직후보다 일정 시간이 지난 뒤 실행되어야 한다. 그래서 서버는 5분 주기로 폴링하고 게시 후 5분이 지난 메시지만 처리한다.

Slack 이벤트를 웹훅으로 수신하는 방식과 비교하면 대기를 위한 지연 실행 처리가 필요 없고, 내부 서버의 엔드포인트를 외부에 노출하지 않는다.

처리 지점은 마지막으로 처리한 메시지의 시각이고, 처리 기록은 답변을 마친 메시지의 목록이다.

처리 지점과 처리 기록은 MongoDB에 저장하므로 서버를 재시작해도 같은 문의를 다시 처리하지 않는다. Orchestrator가 결과 없이 실패한 문의는 오류 안내를 게시한 뒤 처리 완료로 기록하므로 재시도하지 않는다.

답변은 문의 후 최소 5분이 지나야 게시되고 주기마다 1건만 처리되므로 문의가 집중되면 대기가 길어진다. 개발자 확인에 30분에서 2시간이 소요되는 문의와 비교하면 이 지연은 작고, 에이전트 실행 뒤에 작성된 댓글이 문맥에서 제외되는 제약은 남는다.

맡은 범위

  • 서버 전체를 혼자 설계하고 구현했다.
  • AI 챗봇 문서 학습 서비스의 실사용을 보류한 뒤 문의 응답 방식을 실행 시점 조회로 재설계했다.
  • 서버 구현 전에 Claude Code 스킬로 같은 방식을 수동 실행해 방향을 확인했다.
  • 에이전트 구조와 프롬프트를 설계하고 사내 서비스 조회 도구와 소스 탐색 도구를 구현했다.
  • Slack 폴링 수신과 소스 색인의 증분 갱신을 구현했다.
  • 로컬 환경에서 동작을 확인했고, 이후 다른 업무로 개발 시간이 줄어 서버 배포와 문의 채널 답변 게시와 품질 검증은 진행하지 않았다.
