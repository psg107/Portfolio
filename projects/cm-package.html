법인단체 패키지 관리 서비스란

기업과 단체가 의뢰하는 맞춤 여행은 고객사마다 일정과 구성 항목이 다르고, 출발 뒤에도 현지 비용이 추가되어 금액이 변경된다. 법인단체 패키지 관리 서비스는 이런 단체 여행을 담당자가 직접 등록하고 관리하는 업무 시스템이다.

이 업무는 구패키지 시스템에서 담당자가 입력하는 수기 예약으로 처리되었다. 신규 패키지 시스템은 미리 구성한 상품의 자동 판매를 전제로 하므로 맞춤 일정과 실계좌 현금 결제를 지원하지 않아, 기획 단계에서 별도 시스템 개발이 결정되었다.

단체 여행 1건은 행사로 등록되고, 행사는 출발일이 다른 출발그룹 여러 개로 나뉜다. 담당자는 출발그룹마다 다음 업무를 처리한다.

  • 여행자 명단 등록과 변경
  • 항공과 숙소와 투어 항목의 원가 입력
  • 입금 확인과 결제 요청
  • 여행자 보험 가입과 취소

구성

관리 서버는 행사와 명단과 결제 기록을 자체 MySQL에 저장한다. 보험 가입과 입금 확인과 항공 예약은 외부 시스템을 호출해 처리하므로, 외부 호출이 실패할 때의 처리가 주된 설계 문제다.

결제 시스템과 그룹 항공 시스템은 호출을 처리하고 상태 변경을 관리 서버로 통지한다.

여행자 일괄 등록

단체 명단은 규모가 커서 담당자가 엑셀 파일로 등록한다. 일부 행에 오류가 있으면 정상 행만 저장할지 파일 전체를 거부할지 결정해야 한다.

정상 행만 저장하는 방식과 비교하면, 파일 전체를 거부하는 방식에서는 담당자가 저장된 행을 구분해 나머지 행만 다시 업로드할 필요가 없다. 관리 서버는 저장 전에 행을 순서대로 검증하고, 오류가 없는 파일만 한 트랜잭션에서 전부 저장한다.

이 등록 경로는 외부 시스템을 호출하지 않으므로 저장 중 실패도 트랜잭션 되돌림으로 처리가 끝난다. 검증은 첫 오류 행에서 중단되므로 오류가 여러 건이면 담당자가 업로드를 반복해야 하지만, 다시 업로드할 범위는 파일 전체로 명확하다.

보험 가입 실패 격리

담당자는 여행자 여러 명을 선택해 보험 가입을 한 번에 요청하고, 관리 서버는 여행자마다 보험사 API를 호출한다. 보험사 호출은 느려지거나 실패할 수 있고 이미 완료된 가입은 DB 트랜잭션으로 되돌릴 수 없다.

전체를 한 트랜잭션으로 묶으면 1명의 실패가 다른 여행자의 저장 결과까지 되돌리고 실패 기록도 함께 사라진다. 그 결과 보험사에는 가입되어 있는데 관리 서버에는 기록이 없는 상태가 발생한다.

관리 서버는 다음 방식으로 실패 범위를 여행자 1명으로 제한한다.

  • 호출 구간에 트랜잭션을 두지 않고 호출 전에 진행 중 상태를 커밋한 뒤 호출 후에 결과를 저장한다.
  • 여행자별 작업을 병렬로 실행하고 예외를 각 작업 안에서 처리한다.
  • 보험사마다 서비스와 클라이언트와 저장 테이블을 분리하고 클라이언트마다 응답 대기 한도를 지정한다.

상태를 먼저 기록하므로 서버가 호출 도중 중단되어도 진행 중 기록이 저장소에 유지된다. 진행 중 기록이 일정 시간을 초과하면 관리 서버는 새 가입 요청을 거부하고 담당자의 재시도 요청으로만 보험사를 다시 호출한다.

새 가입은 보험 기록을 새로 생성하고 재시도는 기존 기록을 다시 사용하므로, 응답을 받지 못한 호출이 있어도 여행자의 보험 기록이 늘어나지 않는다. 자동 재호출과 비교하면 담당자의 요청이 한 번 더 필요하지만, 결과를 알 수 없는 호출을 다시 보내는 시점은 담당자가 결정한다.

입금 매칭의 부분 성공

고객사의 계좌 입금은 정산 시스템에 기록되고, 담당자는 입금 1건의 금액을 여러 출발그룹에 배분한다. 이 배분을 출발그룹의 결제에 연결하는 일이 입금 매칭이고, 정산 시스템은 배분 목록을 한 번에 받아 배분별 성공 여부를 반환한다.

일부 배분만 실패할 때 전체를 실패로 처리하면 정산 시스템에는 매칭이 있고 관리 서버에는 결제 기록이 없는 상태가 발생한다. 관리 서버는 성공한 배분만으로 결제 기록을 생성해 정산 시스템의 매칭과 결제 기록을 일치시키고, 실패한 출발그룹과 사유는 오류 응답으로 반환한다.

오류 응답을 반환하면 요청 처리 트랜잭션이 되돌아가므로, 매칭 요청과 결제와 결과는 각각 별도 트랜잭션으로 커밋해 유지한다. 이 구조에서는 오류 응답이 전체 실패를 뜻하지 않으므로, 담당자는 매칭 내역 화면에서 출발그룹별 성공과 실패를 확인해야 한다.

번호 발급과 행 잠금

행사번호와 출발그룹번호에는 날짜별 일련번호가 포함되고, 보험사 1개사의 요청에는 서비스 전체에서 증가하는 일련번호가 포함된다. 보험 일련번호는 여행자별 병렬 작업이 동시에 요청하므로 같은 값의 중복 발급을 방지해야 한다.

관리 서버는 날짜별 번호와 보험 일련번호마다 키를 두고, 키의 행을 잠근 뒤 값을 증가시킨다.

방식동작이 서비스에 적용할 때
자동 증가 컬럼DB가 테이블 단위로 번호를 증가시킨다.날짜별 번호와 키별 번호를 표현하지 못한다.
Redis 증가 연산Redis가 키 단위로 번호를 증가시킨다.Redis가 없는 구성에 번호 발급만을 위해 저장소를 추가해야 한다.
DB 행 잠금키마다 행을 두고 잠근 뒤 값을 증가시킨다.기존 MySQL만으로 동작한다.

보험 일련번호는 별도 트랜잭션으로 먼저 커밋한다. 그래서 보험사 응답을 기다리는 동안 잠금을 보유하지 않고, 병렬 호출은 번호 증가 구간에서만 순서대로 처리된다.

보험 일련번호 발급 경로를 기준으로 표시한다.

응답 대기 동안 잠금을 보유하는 방식과 비교하면, 보험사 호출이 실패할 때 일련번호에 빈 값이 생기는 대신 다른 여행자의 번호 발급이 보험사 응답을 기다리지 않는다.

행사번호와 출발그룹번호는 등록 트랜잭션에 참여하므로 등록이 실패하면 번호도 함께 되돌아가고, 등록이 끝날 때까지 같은 날짜의 다른 등록은 대기한다.
