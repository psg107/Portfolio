패키지 여행 예약 서비스란

패키지 여행 한 건은 항공과 호텔과 투어처럼 관리하는 시스템이 서로 다른 상품을 묶어 판매한다. 고객이 결제를 마쳐도 좌석과 객실은 각 공급 시스템이 승인해야 확보되고, 승인에 걸리는 시간도 시스템마다 다르다.

예약 서비스는 결제가 끝난 주문을 예약으로 저장하고 공급 시스템의 승인 결과를 모아 예약 상태를 관리하는 서버이며, 취소와 환불도 처리한다. 공급 시스템이 예약을 거부하거나 요청이 실패해도 예약 서비스는 결과를 기록하고, 담당자는 기록된 지점부터 후속 처리를 진행한다.

구성

예약 서비스는 요청을 받는 API와 메시지를 소비하는 수신기와 정해진 시각에 실행되는 배치로 구성된다. 상품과 재고는 별도의 상품 서비스가 관리하고, 예약 서비스는 HTTP로 호출한다.

공급 시스템은 좌석과 객실을 실제로 확보하는 별도 시스템이고, 공급 예약은 공급 시스템별로 저장하는 예약 기록이다. 가예약은 결제 직전에 생성하는 임시 예약이고, 외부 예약 요청은 공급 시스템에 좌석과 객실을 요청하는 호출이다.

고객 화면의 접수 요청이 예약 문서를 저장하고, 커밋 후 발행한 SQS 메시지가 외부 예약 요청을 시작한다. 결제 승인 통보는 결제 항목별 Redis 키를 획득한 뒤 금액을 대조하고, 첫 결제의 통보는 고객이 화면을 떠난 경우에 대비해 같은 접수 경로를 시작하는 지연 메시지를 발행한다.

공급 시스템이 Kinesis로 발행한 상태 이벤트는 공급 예약 상태에 반영되고, 처리에 실패한 이벤트는 MongoDB에 보관된 뒤 배치가 재처리한다. 보험 가입은 예약 상태 전이와 분리된 배치가 출발 직전에 실행한다.

실패와 반려의 처리 경로

외부 예약 요청이 정상 승인되지 않는 원인은 일시 오류일 수도 있고 공급 시스템의 예약 거부일 수도 있다. 거부된 예약은 다시 요청해도 효과가 없으므로 전체 취소로 이어져야 하고, 일시 오류는 담당자가 다시 요청할 수 있어야 한다.

예약 서비스는 결과를 반려와 실패로 구분한다. 반려는 공급 시스템이 예약을 거부했다고 판단한 경우이고, 실패는 그 밖의 오류다.

구분 분기는 호텔과 투어 연동에 이미 있었지만 후속 처리는 공급 시스템마다 달랐다. 호텔과 투어는 이벤트 처리 코드 안에서 전체 취소와 알림을 직접 실행하고 그 과정의 예외를 무시했으며, 항공 시스템의 거부 응답은 전체 취소로 이어지지 않고 실패로 기록되었다.

현재 구조는 반려와 실패를 서로 다른 SQS 큐에 발행하고, 큐마다 처리 코드 하나가 후속 처리를 담당한다. 외부 예약 요청의 응답과 상태 이벤트와 대기 예약의 거부가 같은 반려 큐로 합류하므로 전체 취소와 담당자 알림의 구현은 하나다.

재연동은 접수 전과 실패 상태의 공급 예약만 다시 요청한다.

이전 구조와 비교하면 전체 취소나 알림이 실패한 메시지는 확인 응답 없이 큐에 남아 제한 시간 후 다시 전달된다. 큐를 거치므로 거부 응답과 전체 취소 사이에 시간 차이가 발생하지만, 외부 예약 요청은 고객 응답 뒤에 실행되므로 고객 응답 시간에는 영향이 없다.

공급 예약이 실패한 예약은 접수 상태로 남고 담당자가 어드민에서 재연동을 실행한다. 자동 재시도와 비교하면 일시 오류에도 담당자 개입이 필요하지만 같은 예약을 자동으로 반복 요청하지 않는다.

수기 예약과 재고 선점

수기 예약은 담당자가 어드민에서 등록한 뒤 고객이 알림톡 링크에서 결제 기한 안에 결제하는 홈쇼핑 상품 예약이다. 등록과 결제 사이에 시간이 있으므로 그동안 금액과 재고와 등록 내용을 유지해야 한다.

가예약은 결제 직전에 생성되어 등록과 수정과 만료를 표현하지 못한다. 수기 예약은 별도 문서로 저장되고, 고객이 결제를 시작하면 이 문서에서 가예약을 생성해 이후 결제와 접수를 일반 예약과 같은 경로로 처리한다.

재고 선점 요청과 해제 단계는 2026년 2월 이전 수기 예약의 경로다.

금액은 등록 시점의 값을 문서에 저장하고 상품 서비스의 현재 금액과 다르면 등록을 거부한다. 등록 내용은 수정할 때마다 버전이 증가하고 이전 버전의 링크는 결제 화면에 접근하지 못한다.

재고는 상품 서비스의 선점 문서로 확보했다. 선점 요청에는 수기 예약 식별자가 필요하므로 문서를 먼저 저장했고, 선점이 실패하면 트랜잭션이 저장을 취소해 재고를 확보하지 못한 링크가 고객에게 전송되지 않았다.

선점에는 결제 기한을 만료일로 전달했으므로 고객이 결제하지 않으면 별도 해제 호출 없이 재고가 반환되었다. 수정할 때는 이전 선점 식별자를 함께 전달했고, 상품 서비스는 새 선점이 검증과 저장을 통과한 뒤에 이전 선점을 해제했다.

이전 선점을 먼저 해제하는 순서와 비교하면 새 선점이 실패해도 이전 선점이 유지되었다. 예약이 완료되면 선점을 해제했고, 해제 실패는 Slack으로 알릴 뿐 완료 처리를 되돌리지 않았다.

등록 요청은 상품 서비스 호출이 모두 끝나야 응답하므로 상품 서비스의 지연이 담당자의 등록 시간으로 이어지고, 호출이 실패하면 담당자가 다시 등록해야 한다. 이 동기 호출을 거치므로 고객에게 전달되는 링크는 금액 대조와 재고 확보를 통과한 상태이고, 등록 시간을 줄이기 위해 검증 호출은 병렬로 실행한다.

2026년 2월 신규 수기 예약의 선점은 공급 시스템 선점 요청으로 대체되었고, 상품 서비스 선점은 이전에 생성된 수기 예약의 처리 경로로 남아 있다.

출발일 예약 분석과 가정 계산

담당자는 출발일 단위로 판매 금액과 원가를 확인하고 금액 조정이나 여행자 추가의 결과를 미리 계산해야 한다. 여행자 수에 따라 적용 금액이 달라지는 항목이 있어 한 예약의 변경도 출발일 전체의 합계에 영향을 미친다.

예약 서비스는 출발일의 예약별 문서를 병렬로 조회해 현재 요약을 생성하고 분석 결과를 Redis에 저장한다. 가정 계산은 저장된 결과를 기준으로 실행하고 실제 예약 문서와 저장된 결과를 변경하지 않으므로, 입력을 달리해 반복해도 결과가 누적되지 않는다.

가정 계산마다 문서를 다시 조회하는 구조와 비교하면 입력을 변경할 때의 조회 비용이 없고 여러 가정이 같은 기준에서 계산된다. 이 구조에서는 분석을 저장한 뒤 변경된 예약이 다음 조회까지 반영되지 않으며, 여러 가정을 같은 기준에서 비교하는 용도이므로 이 시간 차이를 허용한다.

현재 요약과 가정 요약은 구현이 다르지만 형식이 같고 같은 집계 코드가 합계를 계산하므로 두 결과의 계산 규칙이 갈라지지 않는다. 여행자를 추가할 때 필요한 객실 수는 상품 서비스의 객실 배정 계산을 호출해 구한다.
