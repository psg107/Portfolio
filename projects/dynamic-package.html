다이나믹 패키지란

항공권과 숙소를 따로 구매하는 고객은 결제를 각각 진행하고 가격과 취소 규정도 상품마다 확인한다.

다이나믹 패키지는 고객이 선택한 항공과 숙소를 주문 하나로 묶어 한 번의 결제로 예약하는 여행 상품 서비스다. 고객은 추천 조합으로 시작하거나 항공과 숙소를 직접 교체하고, 화면은 합산 금액을 표시한다.

항공과 숙소는 공급 시스템이 서로 달라 가격과 재고가 따로 변한다. 따라서 변동하는 요금을 목록에 빠르게 표시하고, 고객이 선택한 상품을 예약 단계까지 같은 상품으로 식별해야 한다.

서비스는 오픈 전이고 개발과 QA 단계이므로 아래 설계는 운영 트래픽으로 검증되지 않았다.

구성

다이나믹 상품 서비스는 고객이 상품을 선택하는 단계를 처리하고 다이나믹 예약 서비스는 결제 이후를 처리한다. 도해의 화살표는 호출 방향이다.

세션은 고객이 선택한 항공과 숙소를 저장하는 문서다. 주문을 접수하면 다이나믹 예약 서비스가 다이나믹 상품 서비스에 스냅샷(주문 시점의 상품 사본)을 요청하고 응답을 주문으로 저장한다.

다이나믹 예약 서비스는 취소 위약금이 낮은 항목부터 순서대로 공급 시스템에 예약한다. 한 항목이라도 실패하면 항목 전체를 역순으로 취소 처리하고 결제를 환불한다.

숙소 목록 페이징

숙소 검색 서비스는 관련도 순서의 후보만 응답하고 요금을 응답하지 않는다. 요금과 재고는 숙소 공급 시스템에 별도로 조회하므로 요금을 확인하지 못한 후보는 검색 결과를 받은 뒤에 탈락한다.

탈락 수를 미리 알 수 없어 페이지 번호로 위치를 계산하면 같은 숙소가 다시 표시된다. 화면의 금액도 항공을 포함한 합산 금액이므로 가격순 정렬을 숙소 검색 서비스에 위임할 수 없다.

그래서 응답은 다음 페이지의 시작 위치를 포함하고 화면은 이 값만 다음 요청에 전달한다. 정렬이나 필터가 변경되면 화면은 시작 위치를 0으로 초기화한다.

페이징 대안판단이유
기존 구현에 필터만 추가제외기존 구현의 시작 위치는 의미가 둘이어서, 필터를 추가하면 화면과 교환하는 값의 해석이 어긋날 위험이 커진다.
페이지 번호 방식제외필터 탈락을 반영하지 못해 숙소가 중복 표시된다.
가격순 전용 색인보류색인 소유와 일정이 정해지면 다시 검토한다.

숙소 목록은 정렬 기준별로 경로를 분리한다. 관련도순은 목표 개수를 채울 때까지 후보를 소량씩 조회하고 가격순은 관련도 상위 후보 집합의 요금을 모두 조회해 금액순으로 정렬한다.

관련도순 반복은 후보가 소진되거나 조회 횟수 상한에 도달하면 목표 개수를 채우지 못해도 종료한다. 초기 구조는 관련도순에서도 후보 집합 전체의 요금을 조회했으나 페이지 크기에 비해 요금 호출이 과다했다.

가격순은 후보 집합 안에서만 정렬하므로 전체 숙소의 금액 순서와 다를 수 있다. 숙소 검색 서비스가 요금을 보유하지 않아 전체 숙소의 요금 조회는 응답 시간 안에 완료되지 않으므로 정렬 범위를 제한한다.

응답은 전체 개수를 포함하지 않는다. 화면이 사용하지 않고 탈락 수를 미리 알 수 없기 때문이다.

숙소 가격 캐시

목록 한 페이지는 후보 여러 건의 요금을 조회하므로 응답 시간이 공급 시스템 호출에 좌우된다. 로컬에서 단계별 소요 시간을 측정해 확인한 대기 원인은 아래 목록이다.

  • 캐시 적재가 키마다 Redis 왕복을 기다린다.
  • 공급사와 후기 캐시가 값이 없는 숙소를 기록하지 않아 값이 채워진 뒤에도 요청마다 미스(캐시에 값이 없는 경우)가 발생한다.
  • 가격순 정렬이 페이지마다 같은 후보 집합을 다시 조회한다.

적재는 응답 경로 밖의 백그라운드에서 실행하고 값이 없는 숙소는 없음 표시로 기록한다. 숙소 검색 후보는 검색 조건별 캐시가 짧은 시간 고정해 재조회를 줄인다.

가격 캐시는 숙소와 투숙 조건과 필터를 키로 사용하고 여러 숙소를 한 번에 읽는다. 없음 표시는 판매할 요금을 확인하지 못한 숙소를 기록한 값이고 공급 시스템 재조회를 줄인다.

캐시 장애는 검색 실패로 이어지지 않는다. Redis 읽기가 실패하면 모든 숙소를 미스로 처리하고 값 하나가 손상되면 해당 키만 미스로 처리한 뒤 백그라운드에서 삭제한다.

세션별 가격순 후보 캐시는 비용이 큰 요금 조회를 줄이지 못하고 검색 재조회만 줄이므로 적용하지 않는다. 측정에서 확인된 다음 페이지 단축은 공유 요금 캐시가 채워진 효과였다.

가격순은 페이지마다 다시 정렬하므로 페이지 사이에 금액이 변동하면 순서가 달라질 수 있고, 화면은 같은 숙소를 한 번만 표시한다.

적재를 응답 밖에서 실행하므로 응답 직후의 같은 요청에는 미스가 다시 발생할 수 있다. 캐시는 최적화 수단이고 적재 실패도 다음 요청의 미스로 복구되므로 응답이 적재 완료를 기다리지 않는다.

요금제 키

숙소 상품은 같은 객실이라도 요금제가 다르면 다른 상품이다. 초기 구조의 세션은 숙소와 객실만 저장했고 예약 단계가 그 객실의 요금 가운데 하나를 다시 선택했으므로 고객이 선택한 요금과 예약 요금이 달라질 수 있었다.

객실 목록과 세션과 주문과 예약은 같은 요금제 키로 상품을 식별한다. 요금제 키는 공급 시스템의 식별값 여러 개를 해시한 값이고 화면은 서버가 응답한 키를 그대로 전달한다.

공급 시스템의 요금은 고객이 선택한 뒤에도 변동할 수 있으므로 다이나믹 예약 서비스는 예약 직전에 요금을 다시 조회한다. 재조회 금액이 결제 금액과 다르면 공급 예약을 요청하지 않는다.

상품 식별 대안제외 이유
판매 코드를 키로 사용같은 조건에서도 호출마다 값이 변경된다.
식별값 연결 문자열퍼센트 기호와 구분 문자가 쿼리 문자열에서 다시 해석될 수 있다.
식별값 없는 요금 제외일부 공급사의 숙소가 모두 목록에서 탈락한다.
투숙 날짜 변경 시 재탐색고객이 확인하지 않은 상품을 판매하게 된다.

일부 공급사는 투숙 날짜가 변경되면 요금제 값도 변경되므로 고객이 상품을 다시 선택해야 한다. 고객이 확인하지 않은 상품을 예약하는 위험과 비교하면 재선택의 불편이 더 작다.

숙소 요금 기준을 한 번에 변경한 첫 시도는 화면이 필수로 읽는 응답 필드를 삭제해 개발 환경 화면에 오류가 발생했고 변경 범위가 넓어 일부만 원복할 수 없었다. 요금제 키 전환은 작은 단위로 나누어 순서대로 배포했고 응답 필드는 화면이 사용을 중단할 때까지 호환 값으로 유지한다.

조회 시점 추천 판정

고객이 선택한 조합이 추천 조합이면 화면은 추천 사유를 표시한다. 세션 생성 때 이 표시를 고정하면 숙소를 교체하거나 공유 링크로 진입해도 표시가 변경되지 않으므로, 다이나믹 상품 서비스는 조회 시점에 판정하고 기획 정책에 따라 하루 단위로 유지한다.

판정 대안제외 이유
세션 고정값 유지교체할 때 삭제해도 공유 진입과 재진입 정책을 충족하지 못한다.
추천 측 단건 판정 API기존 추천 조회 결과로 판정이 가능하다.
조회마다 다시 판정추천 결과가 갱신될 때마다 같은 조합의 표시가 하루에도 여러 번 변경된다.

다이나믹 상품 서비스는 세션의 검색 조건으로 기존 추천 결과를 조회한 뒤 현재 조합이 포함되는지 대조한다. 숙소는 식별자로 대조하고 항공은 가는 편과 오는 편의 출발 시각이 추천 시간대 안인지 대조한다.

판정은 한국 시각 기준 날짜와 조합을 키로 그날 끝까지 보관한다. 추천 조회가 실패하면 표시 없음을 짧게 보관해 장애 중의 화면 조회가 추천 호출을 기다리지 않고, 같은 키에 값이 있으면 기존 판정을 유지한다.

추천 결과는 항공을 출발 시간대로 응답하므로 같은 시간대의 다른 항공편도 추천으로 표시한다. 새로운 API 없이 기존 조회 결과로 판정하는 범위에서 이 차이를 수용한다.

보관된 판정과 추천 결과 캐시가 모두 없는 조회는 추천 호출을 기다린다.

아키텍처 규칙 검사

다이나믹 상품 서비스는 여러 개발자가 동시에 수정한다. 기존 이름 테스트는 지정한 패키지 안의 클래스만 검사했으므로 규칙 밖 패키지에 둔 파일은 검사를 통과했다.

규칙 대안제외 이유
허용 접미사 목록목록 대부분에 지정된 패키지가 없어 어느 패키지에 있어도 통과한다.
모든 역할에 접미사 강제서비스 클래스의 역할이 합의되어 있지 않아 접미사를 정할 근거가 부족하고 이름을 변경할 범위가 넓다.

구조 테스트 라이브러리 Konsist로 작성한 규칙이 위반을 빌드 실패로 처리하고 서비스의 레이어드 구조는 유지한다. 기존 위반은 기준선(도입 시점 위반과 측정 수치 목록)에 기록해 유예한다.

기준선에 측정 수치가 포함되므로 유예 중인 위반도 수치가 악화되면 빌드가 실패한다. Konsist 검사는 대상이 0개이면 통과하므로 대상 수가 규칙의 하한에 미달해도 빌드 실패로 처리한다.

이름 규칙은 애노테이션이나 상위 타입이 역할을 드러내는 타입에만 접미사 하나와 패키지 하나를 지정한다. 서비스 클래스의 신규 이름 위반은 차단하지 못하지만 근거 없는 접미사를 강제하는 대규모 이름 변경의 회귀 위험과 비교해 이 범위를 수용한다.

컨트롤러에 업무 로직이 있는지처럼 의미 판단이 필요한 항목은 개발자가 코드 리뷰로 확인한다.

맡은 범위

여러 개발자가 스프린트 단위로 작업을 나누어 개발하고 PR 리뷰로 함께 개선했다. 다음 항목을 직접 개발했다.

  • 숙소 목록의 검색 연동과 페이징과 정렬과 필터를 개발했다.
  • 숙소 가격 캐시와 검색 후보 캐시를 작성하고 단계별 측정으로 지연 원인을 분석했다.
  • 요금제 키 전환을 단위별로 설계해 다이나믹 상품 서비스와 숙소 예약 요금 선택에 적용했다.
  • 예약 직전 재조회 금액과 결제 금액을 비교해 다르면 공급 예약을 요청하지 않는 처리를 추가했다.
  • 조회 시점 추천 판정을 개발했다.
  • 다이나믹 상품 서비스의 Konsist 규칙과 기준선을 작성하고 임시 위반 파일로 규칙 동작을 확인했다.
