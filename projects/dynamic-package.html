다이나믹 패키지란

다이나믹 패키지는 고객이 선택한 항공과 숙소를 주문 하나로 묶어 한 번의 결제로 예약하는 여행 상품 서비스다. 고객은 추천 조합으로 시작하거나 항공과 숙소를 직접 교체하고, 화면은 합산 금액을 표시한다.

항공과 숙소는 공급 시스템이 서로 달라 가격과 재고가 따로 변한다. 따라서 변동하는 요금을 목록에 빠르게 표시하고 고객이 선택한 상품을 예약까지 같은 상품으로 식별해야 한다.

서비스는 오픈 전이고 개발과 QA 단계이므로 아래 설계는 운영 트래픽으로 검증되지 않았다.

구성

다이나믹 상품 서비스는 고객이 상품을 선택하는 단계를 처리하고 다이나믹 예약 서비스는 결제 이후를 처리한다. 세션은 고객이 선택한 항공과 숙소를 저장한 문서다.

숙소 목록 페이징

숙소 검색 서비스는 조건에 맞는 후보의 순서만 응답하고 가격은 공급 시스템에 따로 조회하므로, 가격을 확인하지 못한 후보는 조회 뒤에 탈락한다. 탈락 수를 미리 알 수 없어 서버가 다음 시작 위치(오프셋)를 응답하고 화면은 이 값을 다음 요청에 그대로 전달한다.

정렬이나 필터가 변경되면 처음부터 다시 조회한다.

가격순 정렬

화면의 금액은 항공을 포함한 합산 금액이고 숙소 검색 서비스는 가격을 보유하지 않으므로 가격순 정렬을 위임할 수 없다.

관련도순은 필요한 만큼만 조회한다. 초기 구조처럼 후보 집합 전체의 가격을 조회하면 페이지 크기에 비해 호출이 과다했기 때문이다.

가격순은 합산 금액을 비교해야 하므로 페이지마다 후보 집합 전체의 가격을 조회하고, 이 비용은 다음 절의 캐시가 줄인다.

숙소 가격 캐시

목록 한 페이지가 후보 여러 건의 가격을 공급 시스템에 조회하므로 응답 시간이 이 호출에 좌우된다. 숙소 가격 캐시는 이 조회를 줄인다.

Redis 읽기 실패가 실시간 조회로 이어지므로 캐시 장애는 검색 실패가 되지 않는다. 값 하나가 손상된 경우에도 그 숙소만 실시간으로 조회한다.

캐시 가격을 먼저 응답하므로 목록 금액은 공급 시스템의 현재 가격과 다를 수 있다. 응답 뒤 재조회가 캐시를 갱신하고, 결제 금액은 다음 절의 예약 직전 대조가 확인한다.

요금제 키

같은 객실이라도 요금제가 다르면 다른 상품이지만 초기 구조의 세션은 숙소와 객실만 저장했다. 따라서 예약 단계가 객실의 요금을 다시 선택했고 고객이 선택한 요금과 달라질 수 있었다.

요금제 키는 고객이 선택한 요금을 객실 목록부터 예약까지 식별하는 값이고 화면과 서버 사이를 오간다.

같은 키의 요금이 없으면 다른 요금제로 대체하지 않는다. 다른 요금을 선택하면 고객이 확인하지 않은 상품을 판매하게 되므로, 결제 뒤 대조에서 실패하면 항목 전체를 취소 처리하고 결제를 환불한다.

일부 공급 시스템은 투숙 날짜가 변경되면 키도 달라지므로 고객이 객실을 다시 선택한다.

키는 공급 시스템의 식별값 여러 개를 해시한 값이다.

식별 대안제외 이유
판매 코드를 키로 사용같은 조건에서도 호출마다 값이 변경된다.
식별값 연결 문자열퍼센트 기호와 구분 문자가 쿼리 문자열에서 다시 해석될 수 있다.
식별값 없는 요금 제외일부 공급 시스템의 숙소가 모두 목록에서 탈락한다.

추천 사유 표시

고객이 고른 조합이 추천 조합과 같으면 화면에 추천 사유를 표시하고, 표시 여부는 세션을 조회할 때 결정한다. 세션 생성 때 고정하면 고객이 숙소를 교체하거나 공유 링크로 진입해도 표시가 변경되지 않기 때문이다.

조회마다 새로 결정하면 추천 결과가 갱신될 때마다 같은 조합의 표시가 하루에도 여러 번 변경되므로, 기획 정책에 따라 결과를 그날 끝까지 보관한다.

표시 여부는 새로운 API 없이 기존 추천 조회 결과로 결정한다.

보관된 결과와 추천 결과 캐시가 모두 없으면 화면 조회가 추천 호출을 기다린다. 따라서 추천 조회가 실패하면 표시 없음을 짧게 보관해 호출 대기를 반복하지 않고, 같은 조합에 이미 값이 있으면 덮어쓰지 않는다.

아키텍처 규칙 검사

다이나믹 상품 서비스는 여러 개발자가 동시에 수정하는데 기존 이름 테스트는 지정한 패키지 안의 클래스만 검사해 규칙 밖 패키지에 둔 파일을 통과시켰다. 그래서 구조 규칙을 구조 테스트 라이브러리 Konsist로 작성해 위반을 빌드 실패로 처리한다.

규칙대상위반 예
패키지 배치최상위 패키지허용 목록 밖의 패키지 추가
순환 의존 금지최상위 패키지패키지 간 상호 참조
서비스 규모서비스 클래스줄 수 또는 생성자 파라미터 한도 초과
코루틴 스코프 생성 위치설정 패키지 밖의 코드서비스에서 스코프 직접 생성

이미 있던 위반은 기준선(도입 시점의 위반 목록과 줄 수 같은 측정 수치)에 기록해 유예하고 새 위반만 차단한다.

기준선은 측정 수치까지 비교하므로 유예 중인 위반도 수치가 악화되면 빌드가 실패한다. Konsist 검사는 대상이 0개이면 통과하므로 대상 수의 하한을 함께 검사한다.

클래스 이름의 접미사 규칙은 역할이 코드로 드러나는 타입에만 적용한다. 모든 역할에 접미사를 강제하면 역할이 합의되지 않은 서비스 클래스까지 대규모 이름 변경이 필요하기 때문이다.

그 결과 서비스 클래스의 새 이름 위반은 차단되지 않는다. 컨트롤러에 업무 로직이 있는지처럼 의미 판단이 필요한 항목도 개발자가 코드 리뷰로 확인한다.
