패키지 여행 상품 서비스란

패키지 여행은 항공과 호텔과 투어를 일정에 따라 묶어 판매하는 상품이다. 같은 상품이라도 출발일마다 가격과 재고와 판매 상태가 다르고, 좌석과 객실의 재고는 상품 서비스 밖의 공급 시스템이 관리한다.

구패키지 시스템에서는 담당자가 예약마다 금액과 일정을 직접 처리해 예약이 늘면 인력도 함께 늘어났다. 상품 서비스는 신규 패키지 시스템에서 상품 구성과 판매 상태 판단을 자동화한다.

상품 약 2만 개의 출발일별 데이터를 다루고 재고 변경 이벤트를 수시로 수신한다. 따라서 공급 시스템의 변경을 판매 상태에 어떻게 반영할지 설계해야 한다.

구성

상품 서비스는 항공 시스템과 호텔과 투어 시스템의 상품을 아이템으로 저장하고, 아이템을 조합한 아이템 그룹과 상품을 다른 서비스에 제공한다. 판매 단위는 아이템과 아이템 그룹과 상품으로 구분한다.

  • 아이템은 공급 단위이고 날짜별 가격과 판매 여부를 보유한다.
  • 아이템 그룹은 아이템을 일정의 몇째 날에 사용하는지 기록하는 예약 단위이고 출발일별 판매 상태를 저장한다.
  • 상품은 아이템 그룹을 모아 고객 화면에 표시하는 단위다.

항공 시스템과 호텔과 투어 시스템의 변경은 Kinesis로 수신하고 완제품 동기화는 SQS로 수신한다. 완제품은 모두투어가 일정과 가격을 하나로 제공하는 상품이고 아이템 1개만 포함한 아이템 그룹으로 표현한다.

같은 호텔과 항공은 여러 상품에 사용되므로 상품 서비스는 공급 단위와 판매 단위를 분리해 아이템을 재사용한다. 공급 단위를 분리했으므로 아이템 하나가 변경되면 그 아이템을 사용하는 아이템 그룹을 모두 다시 계산해야 한다.

아이템과 아이템 그룹은 날짜별 데이터를 MongoDB 문서 하나에 포함하므로 서로 다른 날짜의 변경도 같은 문서를 수정한다. 주요 문서는 낙관적 락으로 보호하며, 낙관적 락은 문서의 version 값이 읽은 시점과 다르면 저장을 실패시키는 방식이다.

처리에 실패한 이벤트는 MongoDB에 보관해 주기적으로 다시 실행한다. 항공 재고 이벤트는 이벤트를 모아 처리하는 지연 집계 큐를 거친다.

재고 이벤트 처리

호텔과 투어의 재고 이벤트는 가용 또는 불가 종류와 날짜 기간을 전달한다. 이벤트 값을 어디까지 신뢰하는지에 따라 정확도와 호출 비용이 달라진다.

방식동작제약
이벤트 값 적용(이전 구현)이벤트 종류를 기간의 모든 날짜에 저장한다.기간 안에서 날짜별로 다른 재고를 구분하지 못하고 늦게 재처리된 이벤트가 최신 값을 과거 값으로 대체한다.
재조회(현재 구현)이벤트를 수신할 때마다 날짜별 수량을 다시 조회한다.이벤트마다 공급 시스템 호출이 발생한다.

재고 동기화는 이벤트를 변경 신호로만 사용한다. 공급 시스템에서 날짜별 수량을 다시 조회하고, 재고 유무가 변경된 날짜가 있을 때만 아이템 문서를 저장하고 변경된 날짜를 내부 메시지로 발행한다.

항공 재고 이벤트는 지연 집계 큐에 모은 뒤 같은 재조회와 저장을 실행한다.

공급 시스템 응답에 없는 날짜는 재고 없음으로 판단하지 않고 기존 값을 유지한다. 재처리도 식별자만 사용해 공급 시스템을 다시 조회하므로 늦게 재처리해도 오래된 값을 적용하지 않는다.

이벤트마다 공급 시스템 호출이 추가되지만 호텔과 투어 이벤트 1건의 재고 조회는 1회로 제한된다. 재고 유무가 변경되지 않은 이벤트는 저장과 전파 없이 종료되므로 이후 처리 비용이 발생하지 않는다.

재고 유무 전파

아이템은 수량 대신 재고 유무만 저장한다. 수량이 10에서 9로 변경되면 전파하지 않고 수량이 0이 되거나 0에서 증가할 때만 아이템 그룹을 다시 계산하므로 전파 횟수가 줄어든다.

판매 상태는 변경 시점에 계산해 아이템 그룹에 저장한다. 읽을 때마다 계산하면 출발일 수만큼 공급 시스템 호출이 필요하다.

아이템에 수량을 저장하지 않으므로 재고 유무가 변경된 이벤트는 재조회와 함께 아이템별 현재 수량 조회를 발생시킨다. 저장된 수량은 이벤트 사이에 실제 수량과 달라질 수 있으므로 판매 상태 계산은 조회한 수량을 기준으로 한다.

아이템 그룹별 실패 격리

변경 날짜 메시지 하나는 그 아이템을 사용하는 여러 아이템 그룹의 판매 상태 갱신으로 이어진다. 전체를 트랜잭션 하나로 실행하면 아이템 그룹 하나의 저장 충돌이 앞서 처리한 아이템 그룹의 저장까지 취소한다.

상태 갱신은 아이템 그룹마다 별도 트랜잭션(REQUIRES_NEW)으로 실행한다. 오류가 발생한 아이템 그룹은 Slack으로 알리고 다음 아이템 그룹을 처리한다.

아이템 그룹마다 변경된 날짜를 일정의 몇째 날인지로 환산해 출발일을 찾는다.

이벤트 1건의 반영이 아이템 그룹 단위로 나뉘므로 일부 아이템 그룹에만 반영된 상태가 허용된다. 판매 상태는 아이템 그룹마다 독립적으로 판단하므로 다른 아이템 그룹의 결과에 의존하지 않는다.

예약 마감 기한은 이벤트 없이 시간이 지나 도래하므로 일일 배치가 아이템 그룹을 일정 크기로 나누어 마감한다. 크기 단위의 트랜잭션이 일시적인 쓰기 충돌로 실패하면 일정 간격으로 제한 횟수까지 재시도한다.

재고 선점

수기 예약은 담당자가 어드민 서비스에서 등록한 뒤 고객이 결제 기한 안에 결제하는 예약이다. 결제 전까지 재고를 확보하지 않으면 다른 예약이 같은 재고를 소진한다.

이 절의 재고 선점은 2026년 2월 이전 수기 예약에 적용한 별도 문서 방식이다. 선점 기록을 어디에 두는지에 따라 변경 범위와 조회 비용이 달라진다.

방식장점제약
공급 시스템에 요청공급 시스템의 재고와 일치한다.공급 시스템마다 선점과 해제 호출과 실패 보상이 필요하다.
아이템에 수량 저장재고 조회가 단순하다.선점 저장이 아이템 문서의 재고 이벤트 저장과 충돌한다.
별도 문서(2026년 2월 이전 구현)공급 시스템과 아이템 문서를 변경하지 않는다.재고를 조회할 때마다 차감 계산이 필요하다.

별도 문서 방식은 선점을 만료일과 함께 문서로 저장하고 재고를 조회할 때마다 공급 시스템 수량에서 유효한 선점을 차감한다. 만료일이 지난 선점은 차감에서 제외되므로 해제 작업 없이 잔여 수량이 증가한다.

차감 계산은 모든 재고 조회에 추가되지만 공급 시스템마다 선점과 해제와 실패 보상을 구현하지 않고 상품 서비스 안에서 수기 예약의 재고를 확보한다.

2026년 2월 신규 수기 예약의 선점은 공급 시스템 선점 요청으로 대체되었다. 별도 문서 방식은 이전에 생성된 수기 예약의 처리 경로로 남아 있다.

가격 달력 동시 계산

가격 달력은 출발일별 최저가와 아이템 그룹 판매 상태의 요약이고 Redis에 캐시한다. 캐시가 없는 상품에 요청이 동시에 도착하면 요청마다 출발일 전체의 요약을 계산한다.

상품 서비스는 Redis 조건부 저장(SET NX)으로 상품별 처리 중 표시를 획득한 요청만 계산한다. 획득한 뒤 캐시를 다시 확인하므로 앞선 요청이 저장한 결과가 있으면 계산하지 않는다.

이전 구현은 응답에 결과가 필요한 호출이 표시를 확인하지 않고 계산했다. 현재는 처리 중 상태만 받아도 되는 조회 API가 즉시 응답하고 그 외의 호출은 표시를 획득할 때까지 재시도한다.

재시도하는 동안 요청 스레드를 점유하지만 같은 상품의 계산을 한 요청으로 제한해 캐시가 없는 상품에 요청이 집중될 때 중복 계산을 줄인다. 처리 중 표시에는 만료 시간이 있어 계산이 중단되어도 표시가 자동으로 해제된다.

맡은 범위

여러 개발자가 스프린트 단위로 작업을 나누어 개발하고 PR 리뷰로 함께 개선했다. 다음 항목을 직접 개발했다.

  • 공급 시스템 재조회 방식의 재고 동기화와 재고 유무 저장을 개발해 이벤트 값 적용 방식을 대체했다.
  • 판매 상태 계산을 재고 동기화와 연결하도록 다시 작성했다.
  • 재고 상태 갱신을 아이템 그룹별 트랜잭션으로 분리하고 오류 알림을 추가했다.
  • 일일 마감 배치의 쓰기 충돌 재시도를 추가했다.
  • 재고 선점의 저장과 검증과 차감 코드 및 테스트와 예약 서비스의 호출부를 개발했다.
  • 가격 달력 캐시의 처리 중 표시와 호출별 대기 방식을 개발했다.
  • 항공 아이템과 항공 시스템 동기화의 초기 구현을 개발했다.
