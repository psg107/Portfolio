통합 검색 서비스란

패키지 여행 상품은 같은 상품이라도 출발일마다 가격과 판매 상태와 항공편이 다르다. 고객은 출발 기간과 항공사 같은 조건으로 검색하고, 검색 결과에는 조건을 충족하는 출발일의 최저가가 표시되어야 한다.

통합 검색 서비스는 사내 공통 검색 서비스와 상품 서비스 사이에서 패키지 상품의 검색 결과를 생성하는 서비스다. 사내 공통 검색 서비스는 상품 수준의 값을 색인하고, 통합 검색 서비스는 출발일 수준의 값을 검색 시점에 결과에 반영한다.

상품 약 2만 개를 다루는 구조에서 검색 요청마다 출발일별 값을 조회하고 계산하면서 응답 시간이 약 8초까지 증가했다. 아래 절의 구조를 적용한 뒤 응답 시간은 1초 미만으로 단축되었고, 측정 조건과 구조별 기여는 기록으로 남아 있지 않다.

구성

검색 세션은 사내 공통 검색 서비스가 검색 요청마다 생성하는 결과 집합이고, 이후 요청은 세션 식별자로 같은 결과 집합을 조회한다. 사내 공통 검색 서비스는 검색 세션에 외부 값을 주입하는 기능도 제공한다.

지역과 테마처럼 상품 수준의 조건은 검색 세션 생성 때 적용된다. 항공사와 가격처럼 출발일마다 다른 조건은 통합 검색 서비스가 MongoDB에 동기화한 출발일별 사본으로 계산해 주입한다.

검색 시점 값 주입

사내 공통 검색 서비스의 색인에는 상품 수준의 값만 있으므로, 출발일 조건으로 필터링하거나 출발일 가격으로 정렬하려면 검색 시점의 값이 필요하다. 통합 검색 서비스는 검색 세션의 후보 상품별로 조건을 충족한 출발일의 최저가를 계산해 세션에 주입한다.

조건을 충족하는 출발일이 없는 상품에는 가격 0을 주입하고, 해당 상품은 검색 세션 생성 시 지정한 '가격이 0보다 큼' 조건에 의해 결과에서 제외된다. 세션이 필터와 정렬과 집계를 함께 처리하므로 통합 검색 서비스에는 별도의 정렬 로직이 없다.

출발 기간을 좁히지 않고 출발일 조건도 없는 요청은 집계를 실행하지 않는다. 동기화 시점에 상품별 대표 출발일을 계산해 색인 문서에 저장하므로 세션은 대표 출발일의 값으로 정렬한다.

후보를 적게 요청해 먼저 응답하고 백그라운드에서 전체 후보로 세션을 다시 생성하는 방식은 적용 후 철회되었다. 최초 응답의 건수가 근사값이어서 정확한 건수인지 알리는 플래그가 화면까지 필요했고, 현재는 후보를 항상 상한까지 요청한다.

정확한 건수를 응답하는 대신 집계 비용은 후보 수에 비례한다. 후보 상품을 일정 크기로 분할해 병렬로 집계해도 쿼리 수는 후보 수에 따라 증가한다.

출발일 값의 저장 위치

최저가를 계산하려면 상품 서비스가 관리하는 출발일별 값이 필요하다. 최초 구조는 검색 요청마다 상품 코드를 분할해 상품 서비스를 동시에 호출했고, 이후 구조는 같은 값을 Redis에 저장해 조회했다.

Redis 구조는 날짜 범위로 최저가 출발일을 먼저 선택한 뒤 사내 공통 검색 서비스가 주입된 값으로 조건을 필터링했다. 그래서 최저가가 아닌 출발일이 항공사 조건을 충족해도 상품이 결과에서 제외되었다.

MongoDB 구조는 조건을 먼저 적용하고 남은 출발일로 최저가를 계산하며, 필터 조건별 인덱스를 별도로 관리한다. 검색 요청이 상품 서비스를 호출하지 않는 대신 상품 변경은 동기화가 끝난 뒤 검색에 반영된다.

같은 조건의 중복 세션 생성 방지

검색 세션 생성과 값 주입은 외부 서비스 호출과 출발일별 집계를 포함하는 작업이고, 같은 검색 조건은 반복해서 요청된다. 통합 검색 서비스는 빈 값을 정규화한 검색 조건을 키로 세션 식별자를 Redis에 저장해 재사용하고, 결과가 없는 조건도 같은 방식으로 저장한다.

캐시가 비어 있는 조건에 요청이 동시에 집중되면 같은 세션 생성이 반복되는 현상(Cache Stampede)이 발생한다. 최초 구조는 캐시를 읽은 뒤 처리 중 표시를 저장했으므로, 읽기와 저장 사이에 도달한 요청은 함께 세션을 생성했다.

현재 구조는 세션 생성이 진행 중임을 알리는 처리 중 표시를 Redis 조건부 저장(SET NX)으로 기록해 저장에 성공한 요청만 세션을 생성한다. 나머지 요청은 간격을 두고 캐시를 다시 확인해 먼저 생성된 식별자를 반환한다.

같은 조건의 집계가 한 번만 실행되는 대신 후속 요청은 세션 생성이 끝날 때까지 결과 없이 대기한다. 재확인 상한을 초과한 요청에는 오류를 응답한다.

만료 전 백그라운드 갱신

캐시가 만료된 뒤에 다시 채우면 만료 직후의 요청이 세션 생성 비용을 모두 부담한다. 통합 검색 서비스는 만료까지 남은 시간이 기준보다 짧은 캐시에 같은 조건의 요청이 도달하면 기존 식별자를 먼저 반환하고, 백그라운드에서 새 세션을 생성해 캐시를 교체한다.

점선은 식별자를 먼저 반환한 뒤 별도 작업이 이어지는 구간이다.

갱신은 갱신 락을 획득한 요청만 실행한다. 갱신 락은 처리 중 표시와 다른 키를 사용해 캐시에 기존 식별자를 남겨 두므로 갱신 중에도 다른 요청은 대기하지 않는다.

요청을 계기로 갱신하므로 요청이 있는 조건에만 비용이 발생하고, 요청이 드문 조건은 만료 후 첫 요청이 세션 생성 비용을 부담한다. 상품 변경은 캐시 유지 시간만큼 검색 결과에 늦게 반영될 수 있다.

캐시 유지 시간은 검색 세션 유효 시간보다 짧게 설정되어 있고, 고객이 만료된 세션을 조회하면 다시 검색하라는 안내를 표시한다.

맡은 범위

여러 개발자가 스프린트 단위로 작업을 나누어 개발하고 PR 리뷰로 함께 개선했고, 검색 영역은 주 담당으로 작업했다. 2024.06부터 2025.01까지 집중해 개발했고, 이후 2025.12까지 수정에 참여했다.

다음 항목을 직접 개발했다.

  • 서비스 초기 구성과 검색 API를 작성했다.
  • 구패키지 시스템과 신규 패키지 시스템의 상품을 같은 색인 문서로 변환하는 경로와 동기화를 다른 개발자와 함께 작성했다.
  • 출발일 값의 조회를 상품 서비스 호출에서 Redis와 MongoDB 사본으로 변경했고, 필터 조건별 인덱스를 구성했다.
  • 검색 세션에 값을 주입하는 흐름과 MongoDB 집계의 분할 병렬 처리를 작성했고, 후보 축소 방식을 적용한 뒤 철회했다.
  • 대표 출발일을 색인 문서에 추가했다.
  • 처리 중 표시를 조건부 저장으로 변경했고, 갱신 락과 만료 전 갱신을 작성했다.

다음 영역은 다른 개발자가 개발했다.

  • 같은 조건의 캐시와 처리 중 대기의 최초 구조
  • 대표 출발일을 사용해 집계를 생략하는 분기
