구패키지 시스템이란

구패키지 시스템은 패키지 여행 상품을 등록해 판매하고 예약을 관리하는 C# 시스템이다. 상품은 일정을 정의한 기초상품과 출발일별 판매 단위인 출발상품으로 나뉘고, 담당자는 어드민에서 수기 예약과 금액 조정을 직접 수행한다.

구패키지 시스템은 2000년대부터 유지해 온 코드에 외부 판매 채널과 제휴 서비스를 계속 연결한다. 기존 화면과 저장 프로시저의 동작을 유지하면서 새 연동과 규칙 변경을 추가하는 것이 유지보수의 주된 과제다.

별도로 개발된 신규 패키지 시스템은 고객의 구매와 예약을 자동으로 처리하고, 구매 실적으로 산정하는 우수회원 등급을 위해 주문 데이터를 구패키지 DB로 전달한다.

구성

신규 패키지 시스템에서 저장 프로시저로 가는 경로는 2024년에 추가되었다.

외부 연동은 네이버 상품 전송과 모두투어 상품 수집과 현대카드 제휴 포인트 조회다.

네이버 상품 전송

네이버 해외패키지 고객은 2021년 변경 이후 네이버 안에서 예약과 결제까지 진행한다. 변경 당시 담당자는 여행 상품 단위인 모상품을 네이버 어드민에 등록했고, 구패키지 시스템은 네이버의 자상품 API로 모상품 아래의 출발일 단위 자상품을 전송한다.

기존 코드는 가격 변경과 마감처럼 변경 종류마다 전송 함수를 따로 두었으므로 이 구조를 유지하면 변경 종류가 늘어날 때마다 전송 함수와 네이버 값 변환 코드가 함께 증가한다. 구패키지 시스템은 변경 종류를 대상 출발상품을 찾는 데만 사용하고 전송 값은 DB의 현재 상태에서 읽는다.

전송 경로는 판매 정보 갱신과 전시 종료(자상품을 예약 마감 상태로 전송하는 처리)로 제한된다. 같은 출발상품을 가리키는 요청이 여러 건이어도 전송 값은 처리 시점의 DB 상태다.

자상품 코드는 기초상품 코드와 항공편과 박일수와 출발일의 조합이다. 이 조합이 같은 출발상품 중 하나가 마감이고 다른 하나가 전시이면 두 상품은 같은 자상품 코드로 전송되므로, 마감 상품을 먼저 전송하고 전시 상품을 나중에 전송한다.

호출이 성공해도 일부 자상품이 실패할 수 있으므로 완료 판정은 호출 결과와 응답 자상품 수와 자상품별 결과를 모두 확인한다. 완료 판정이 요청 단위이므로 일부 자상품만 실패해도 요청 전체를 실패로 기록한다.

현재 상태 전체를 전송하면 기초상품 변경 요청이 소속 출발상품 전체의 전송으로 이어져 전송량이 증가한다. 모상품별로 요청을 분할해 전송 수 제한을 지키고, 변경 종류가 늘어도 전송 코드가 증가하지 않으므로 이 전송량을 수용한다.

청구할인 판정

청구할인은 특정 카드로 결제하면 카드사 청구 금액을 할인하는 행사다. 담당자는 행사마다 적용 범위와 제외 범위를 상품 유형과 지역과 상품 코드 단위로 등록하고, 결제 화면은 범위를 판정해 할인 안내를 표시한다.

기존 판정 코드는 예약 결제와 추가 결제와 분할 결제 화면에 복제되어 있었고 값 비교 방식과 제외 범위 확인 순서가 화면마다 달라 같은 행사의 표시 결과도 달라질 수 있었다. 이 구조에서 등록한 범위대로 할인이 표시되지 않는다는 조건 수정 요청이 접수되었다.

수정 방식에 따라 이후 규칙을 변경할 때 배포하는 대상이 달라진다.

  • 화면별로 수정하면 변경량이 가장 적지만 복제된 규칙이 유지되어 차이가 다시 생길 수 있다.
  • 공용 라이브러리로 이동하면 DLL 파일을 화면 저장소마다 교체해 반영하므로 규칙 변경마다 화면 서버를 함께 배포한다.
  • API로 이동하면 PC 결제 화면은 API의 판정 결과만 사용하고 규칙 변경은 API 배포로 반영된다.

PC 결제 화면은 판정을 API에 요청한다. 판정 순서는 적용 범위와 제외 범위와 예산 순서로 고정되고, 제외 범위에 해당하는 행사는 적용 범위에 해당해도 목록에서 제외된다.

판정을 API로 이동하면 결제 화면이 API 응답에 의존한다. 할인 안내 조회의 실패가 결제 진행에 영향을 주지 않도록 조회 실패를 할인 없음으로 처리한다.

판정 API의 코드 구조

API 서버의 기존 코드는 서비스 클래스가 저장 프로시저를 호출한다. 판정 API는 같은 서버의 별도 프로젝트에 위치하고 유스케이스와 포트와 어댑터로 코드를 나누며, 저장 프로시저 대신 Entity Framework로 데이터를 읽는다.

기존 방식과 비교하면 판정 규칙이 유스케이스 클래스 하나에 C# 코드로 위치하므로 규칙을 수정할 때 저장 프로시저를 변경하지 않고 API 서버만 배포한다.

같은 API 서버에 기존 구조와 새 구조가 함께 유지되므로 서버를 수정하는 개발자는 프로젝트별 방식을 구분해야 한다. 기존 API까지 이동하면 청구할인 수정을 넘어서는 변경이 되므로 기존 코드는 유지된다.

신규 패키지 주문 전달

신규 패키지 시스템의 예약은 MongoDB에 저장되고, 우수회원 등급 산정에 사용하는 주문 집계는 구패키지 DB의 저장 프로시저가 수행한다. 신규 패키지 고객의 구매 실적을 등급에 반영하려면 두 저장소를 연결해야 하므로 이 전달 경로는 2024년에 추가되었다.

연결 방식에 따라 양쪽 시스템의 변경 범위가 달라진다.

신규 패키지 주문은 전용 적재 테이블을 거쳐 집계된다. 기존 집계 프로시저의 변경이 읽는 대상 추가로 제한되므로 다른 사업의 주문 처리는 변경되지 않는다.

전송 배치는 기존 집계 프로시저가 같은 예약을 읽는 날보다 먼저 실행되므로 실패 건을 재전송할 시간이 있다.

전용 적재 테이블을 사용하면 신규 패키지 시스템의 예약 서비스가 구패키지 DB에 의존한다. 이 경로의 DB 호출은 호출 클래스 하나로 제한되고, 전송 단위를 예약 단위로 수정한 2025년 변경도 Kotlin 코드 수정만으로 반영되었다.

맡은 범위

여러 개발자가 작업을 나누어 유지보수와 기능 개발을 진행했다. 다음 항목을 직접 개발했다.

  • 네이버 자상품 전송 서비스와 변경 종류 분기와 완료 판정을 개발했고, 이후 자상품 코드 규칙 변경과 마감 상품 우선 전송을 추가했다.
  • 청구할인 조건 수정 요청을 받아 판정을 API로 이동하고 PC 결제 화면의 복제 코드를 삭제했다.
  • 포트와 어댑터 구조의 프로젝트를 먼저 API 서버에 추가했고 판정 API를 이 프로젝트에 작성했다.
  • 신규 패키지 시스템 개발 기간인 2024년에 주문 전달 배치와 호출 코드와 적재 프로시저를 작성하고 기존 집계 프로시저에 신규 패키지 주문을 추가했다.
  • 현대카드 제휴 포인트의 PC 결제 화면과 추가 결제 화면을 개발했다.
  • 모두투어 연동을 재개하고 상품 파일 수집의 통신 실패 재시도를 추가했다.

다음 영역은 다른 개발자가 개발했다.

  • 네이버 변경 대기 테이블과 2023년 이후의 모상품 연동
  • 현대카드 연동 라이브러리의 초기 작업과 간편결제 API 변경
  • 모두투어 수집 배치와 정산 배치
  • 주문 전달의 전체 취소 제외 규칙
