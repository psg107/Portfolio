구패키지 시스템이란

구패키지 시스템은 패키지 여행 상품을 등록해 판매하고 예약을 관리하는 C# 시스템이다. 상품은 일정을 정의한 기초상품과 출발일별 판매 단위인 출발상품으로 나뉜다.

2000년대부터 유지해 온 코드에 판매 채널과 규칙 변경이 계속 추가되므로 변경 범위를 좁게 유지하는 것이 설계의 기준이다. 2023년부터는 고객의 구매와 예약을 자동으로 처리하는 Kotlin 신규 패키지 시스템이 별도로 개발되었다.

구성

네이버 상품 전송

네이버 고객은 네이버 안에서 예약과 결제까지 진행하므로 구패키지 시스템은 네이버에 등록된 여행 상품 아래로 출발상품을 API로 전송한다. 기존 코드처럼 변경 종류마다 전송 함수를 두면 종류가 늘 때마다 전송 코드와 값 변환 코드가 함께 증가한다.

그래서 변경 종류는 전송 대상을 찾는 데만 사용하고 전송 값은 DB의 현재 가격과 전시 상태(판매 화면 표시 여부)에서 읽는다. 전시 종료 요청만 DB 값과 무관하게 마감으로 전송한다.

현재 상태 전체를 전송하므로 기초상품 하나의 변경이 소속 출발상품 전체의 전송으로 이어지는 대신, 변경 종류가 늘어도 전송 코드는 증가하지 않는다.

네이버 상품 코드는 출발일까지 포함해도 출발상품마다 고유하지 않다. 같은 기초상품과 출발일에 항공편과 박일수까지 같은 출발상품이 있기 때문이다.

이때 마감 상품과 전시 상품이 같은 코드로 전송될 수 있으므로 마감 상품을 먼저 전송해 전시 상태가 마지막에 도착하게 한다.

청구할인 판정

청구할인은 특정 카드로 결제하면 카드사 청구 금액을 할인하는 행사이고, 결제 화면은 담당자가 등록한 적용 범위와 제외 범위로 행사를 판정해 안내를 표시한다. 결제 화면마다 판정 코드가 복제되어 있었고 비교 방식이 서로 달라 같은 행사의 표시도 달라질 수 있었다.

할인 조건을 수정해 달라는 요청을 화면별로 반영하면 복제가 유지되고, 공용 라이브러리로 이동하면 DLL을 화면 저장소마다 교체해 규칙 변경마다 화면 서버를 배포해야 한다. 판정을 API 서버의 C# 코드에 두면 결제 화면은 결과만 사용하고 규칙을 수정할 때 저장 프로시저 변경 없이 API만 배포한다.

결제 화면이 API 응답에 의존하게 되므로, 할인 안내 조회의 실패가 결제 진행에 영향을 주지 않게 조회 실패를 할인 없음으로 처리한다.

신규 패키지 주문 전달

우수회원 등급은 구매 실적으로 산정하고 집계 프로시저는 구패키지 DB에 있다. 신규 패키지 예약은 MongoDB에 저장되므로 그대로는 집계에 반영되지 않는다.

2024년에 추가한 주문 전달 배치가 신규 패키지 예약을 구패키지 DB의 전용 적재 테이블에 저장하고, 기존 집계 프로시저는 이 테이블을 읽는 대상으로 추가한다. 기존 프로시저의 변경이 읽는 대상 추가로 제한되어 다른 사업의 주문 처리는 변경되지 않는다.

대신 신규 패키지 시스템이 구패키지 DB에 접속하며, 이 경로의 의존은 호출 클래스 하나로 제한된다.

전송 배치는 기존 집계 프로시저가 같은 예약을 읽는 날보다 먼저 실행되므로 실패 건을 재전송할 시간이 있다.

맡은 범위

여러 개발자가 작업을 나누어 유지보수와 기능 개발을 진행했다. 다음 항목을 직접 개발했다.

  • 네이버 출발상품 전송을 개발하고 이후 상품 코드 규칙 변경과 마감 상품 우선 전송을 추가했다.
  • 청구할인 조건 수정 요청을 받아 판정을 API로 이동하고 PC 결제 화면의 복제 코드를 삭제했다.
  • 2024년에 주문 전달 배치와 적재 프로시저를 개발하고 기존 집계 프로시저에 신규 패키지 주문을 추가했다.

다음 영역은 다른 개발자가 개발했다.

  • 네이버 변경 요청을 기록하는 대기 테이블
  • 네이버 여행 상품 등록 연동
